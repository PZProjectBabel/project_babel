## ภาพรวมโครงการ

**Project Babel** คือไปป์ไลน์การแปลอัตโนมัติที่ออกแบบมาโดยเฉพาะสำหรับการแปลม็อดจาก Steam Workshop ของเกม *Project Zomboid* ด้วย AI หลายภาษา

### ที่มาและแรงจูงใจ

Project Zomboid มีระบบนิเวศม็อดที่กว้างขวาง โดยมีม็อดที่ผู้เล่นสร้างขึ้นมากมายนับหมื่นบน Steam Workshop ม็อดส่วนใหญ่มีเฉพาะข้อความภาษาอังกฤษ ทำให้ผู้เล่นที่ไม่ใช้ภาษาอังกฤษพบกับอุปสรรคด้านภาษาเมื่อใช้งานม็อดเหล่านี้ วิธีการแปลด้วยมนุษย์แบบเดิมเผชิญกับความท้าทายหลักสองประการ:

1. **ขนาดที่ใหญ่หลวง**: ม็อดมีจำนวนมากและมีข้อความปริมาณมหาศาล ทำให้ต้นทุนการแปลด้วยมนุษย์สูงมากและดำเนินการได้ช้า
2. **การอัปเดตอย่างต่อเนื่อง**: ผู้สร้างม็อดอัปเดตเนื้อหาบ่อยครั้ง การแปลจึงต้องติดตามอย่างต่อเนื่อง มิฉะนั้นจะล้าสมัยและใช้ไม่ได้

Project Babel แก้ปัญหาเหล่านี้ด้วยการสร้างไปป์ไลน์การแปลด้วย AI แบบอัตโนมัติเต็มรูปแบบ สามารถค้นพบม็อดใหม่โดยอัตโนมัติ ดาวน์โหลดไฟล์ม็อด แยกข้อความที่ต้องแปล ใช้โมเดลภาษาขนาดใหญ่ (LLM) สร้างคำแปลคุณภาพสูง และส่งออกแพตช์ภาษาแปลที่ผู้เล่นสามารถนำไปใช้ได้ทันที

### ความสามารถหลัก

- **การค้นพบอัตโนมัติ**: รวบรวมรหัสม็อดที่ต้องแปลโดยอัตโนมัติจากแพลตฟอร์มชุมชน (AsOne) และรายการคำขอในเครื่อง
- **การแปลอัจฉริยะ**: รวมคลังข้อความอ้างอิง (การค้นคืนแบบ RAG) และอภิธานศัพท์ โดย LLM จะสร้างคำแปลที่รับรู้บริบท
- **การอัปเดตแบบเพิ่มหน่วย**: ตรวจจับการเปลี่ยนแปลงเนื้อหาของม็อด แปลเฉพาะข้อความที่เพิ่มหรือแก้ไขใหม่ หลีกเลี่ยงการทำงานซ้ำซ้อน
- **การตรวจสอบความปลอดภัย**: ตรวจจับและกรองม็อดที่มีเนื้อหาละเมิด (ยาเสพติด เนื้อหาทางเพศ ฯลฯ) โดยอัตโนมัติ
- **รองรับหลายภาษา**: สถาปัตยกรรมของไปป์ไลน์รองรับภาษาปลายทาง 27 ภาษา ปัจจุบันให้บริการหลักสำหรับภาษาจีนตัวย่อ (zh-hans)
- **การทำงานต่อเนื่อง**: เรียกผ่านตัวกำหนดเวลาของ GitHub Actions ทำให้สามารถอัปเดตคำแปลได้โดยไม่ต้องมีการดูแล

### วัตถุประสงค์ของเอกสาร

เอกสารนี้จัดทำขึ้นสำหรับนักพัฒนาที่ต้องการทำความเข้าใจ ติดตั้งใช้งาน หรือมีส่วนร่วมในไปป์ไลน์ Project Babel การอ่านเอกสารนี้จะช่วยให้คุณ:

- เข้าใจสถาปัตยกรรมโดยรวมและทิศทางการไหลของข้อมูลของไปป์ไลน์
- เข้าใจหน้าที่และหลักการภายในของแต่ละโมดูลประมวลผล
- ทำความเข้าใจโครงสร้างของไฟล์กำหนดค่าและความหมายของพารามิเตอร์ต่าง ๆ
- มีความสามารถในการรันไปป์ไลน์ในสภาพแวดล้อมท้องถิ่นหรือ CI

## 1. สถาปัตยกรรมระบบ

### สถาปัตยกรรมโดยรวม

ไปป์ไลน์ใช้สถาปัตยกรรมแบบ "ไปป์ไลน์" คลาสสิก ประกอบด้วยโมดูลอิสระ 14 โมดูลที่เรียงต่อกันตามลำดับ แต่ละโมดูลรับผิดชอบงานย่อยที่ชัดเจนเพียงงานเดียว โมดูลต่าง ๆ ส่งผ่านข้อมูลระหว่างกันผ่านโครงสร้างข้อมูลในหน่วยความจำ และในที่สุดสร้างไฟล์คำแปลที่พร้อมเผยแพร่

```mermaid
flowchart TD
    A[ConfigReader] --> B[RepoDataLoader]
    B --> C[ModIdCollector]
    C --> D[ModInfoFetcher]
    D --> E[ModDownloader]
    E --> F[ContentExtractor]
    F --> G[ContentChecker]
    G --> H[EmbeddingFetcher]
    H --> I[TranslationBatcher]
    I --> J[RagContextRetriever]
    J --> K[LLMTranslator]
    K --> L[ResultWriter]
    L --> M[FinalOutputWriter]
    M --> N[ProgressReporter]

    subgraph การซิงโครไนซ์คำแปลอ้างอิง
        B2[RepoDataLoader-ref] --> D2[ModInfoFetcher-ref]
        D2 --> E2[ModDownloader-ref]
        E2 --> F2[ContentExtractor-ref]
        F2 --> H2[EmbeddingFetcher-ref]
        H2 --> L
    end
```

> **หมายเหตุ**: ในเส้นทางการซิงโครไนซ์คำแปลอ้างอิง `RepoDataLoader-ref` จะโหลดข้อมูลแคชจากไดเรกทอรี `translation_ref/` เป็นจุดเริ่มต้น แทนที่จะรับอินพุตจาก `ConfigReader`

### สองขั้นตอนการประมวลผลหลัก

ไปป์ไลน์ประกอบด้วยเส้นทางการประมวลผลแบบขนานสองเส้นทาง ซึ่งให้บริการตามวัตถุประสงค์ที่แตกต่างกัน:

| ขั้นตอน | เส้นทาง | วัตถุที่ประมวลผล | วัตถุประสงค์ |
|---------|---------|------------------|-------------|
| **การซิงโครไนซ์คำแปลอ้างอิง** | กราฟย่อยด้านล่างในรูป | ม็อดภาษาแปลคุณภาพสูงที่มีอยู่แล้ว (`translation_ref/`) | สร้างคลังข้อความอ้างอิงสำหรับการค้นคืนแบบ RAG |
| **การแปลหลัก** | เส้นทางหลักด้านบนในรูป | ม็อดทั่วไปที่ต้องแปล (`data/`) | ดำเนินการแปลด้วย AI จริง |

ในที่สุดทั้งสองเส้นทางจะรวมเข้าสู่ `ResultWriter` และ `FinalOutputWriter` เพื่อสร้างไฟล์สำหรับเผยแพร่แบบรวมศูนย์

ข้อดีของการออกแบบแยกนี้คือ: ม็อดคำแปลอ้างอิงมักได้รับการแปลอย่างพิถีพิถันโดยมนุษย์ ควรดูแลรักษาอย่างอิสระและซิงโครไนซ์เป็นลำดับแรก ในขณะที่การแปลหลักจะประมวลผลม็อดจำนวนมากที่ต้องแปลด้วย AI ความถี่ในการเปลี่ยนแปลงและตรรกะการประมวลผลของทั้งสองแตกต่างกัน การแยกจัดการจะช่วยหลีกเลี่ยงการรบกวนซึ่งกันและกัน

### การไหลของข้อมูลหลัก

จากมุมมองระดับสูง เส้นทางการไหลของข้อมูลในไปป์ไลน์มีดังนี้:

```
config.json / secrets.json
    → การรวบรวมรหัสม็อด (ชุมชน AsOne + คำขอในเครื่อง)
    → การค้นหาข้อมูลเมตาจาก Steam (ชื่อ ผู้แต่ง เวลาอัปเดต ฯลฯ)
    → การดาวน์โหลดไฟล์ม็อดด้วย steamcmd
    → การแยกข้อความ (แปลงเป็นออบเจ็กต์ TranslationEntry)
    → การตรวจสอบความปลอดภัยของเนื้อหา (กรองเนื้อหาที่ละเมิด)
    → การคำนวณเวกเตอร์ฝัง (เตรียมสำหรับการค้นคืนแบบ RAG)
    → การจัดกลุ่มเป็นชุด (TranslationBatch พร้อมการควบคุมงบประมาณโทเค็น)
    → การค้นคืนความคล้ายคลึงแบบ RAG (จับคู่คำแปลอ้างอิงเป็นบริบท)
    → การแปลด้วย LLM (เรียกโมเดลภาษาขนาดใหญ่เพื่อสร้างคำแปล)
    → การเขียนผลลัพธ์กลับแคช (data/translations/)
    → การส่งออกขั้นสุดท้าย (final_outputs/project_babel/)
```

ผลลัพธ์ของแต่ละขั้นตอนคืออินพุตของขั้นตอนถัดไป ก่อให้เกิด "สายการผลิตข้อมูล" ที่สมบูรณ์ แต่ละโมดูลในไปป์ไลน์จะถูกอธิบายโดยละเอียดในส่วนที่ 3

## 2. ขั้นตอนการทำงานของไปป์ไลน์

ตรรกะทั้งหมดของไปป์ไลน์ถูกจัดลำดับโดยเมธอด `PipelineRunner.RunAsync()` ใน `Program.cs` ซึ่งประกอบด้วยขั้นตอนการประมวลผลประมาณ 20 กว่าขั้นตอน เพื่อให้เข้าใจง่าย เราจะแบ่งขั้นตอนเหล่านี้ออกเป็นสี่ระยะตามหน้าที่ อธิบายเนื้อหางานและวัตถุประสงค์การออกแบบของแต่ละระยะดังนี้

### ระยะที่ 1: การโหลดการกำหนดค่า (ขั้นตอนที่ 1)

จุดเริ่มต้นของทุกอย่างคือการโหลดและตรวจสอบไฟล์กำหนดค่า แม้ว่าระยะนี้จะเรียบง่าย แต่เป็นพื้นฐานสำหรับความเสถียรของไปป์ไลน์ทั้งหมด — ข้อผิดพลาดในการกำหนดค่าใด ๆ ควรถูกตรวจพบและยุติโดยทันที เพื่อหลีกเลี่ยงการสิ้นเปลืองทรัพยากรในการประมวลผล

- `ConfigReader.LoadConfig()` รับผิดชอบอ่าน `config/config.json` (พารามิเตอร์ของไปป์ไลน์) และ `config/secrets.json` (คีย์ลับ)
- หลังจากโหลดเสร็จจะตรวจสอบฟิลด์บังคับทั้งหมดทันที: หาก LLM API Key ว่างเปล่า แสดงว่าไม่สามารถเรียกใช้บริการแปลได้ จะเรียก `Environment.Exit(1)` เพื่อยุติกระบวนการ ทันที หลีกเลี่ยงการเข้าสู่ขั้นตอนการประมวลผลที่ไร้ความหมายในภายหลัง
- พร้อมกันนี้จะแยกวิเคราะห์ `config/supported_languages.json` เพื่อโหลดคำจำกัดความของภาษาทั้ง 27 ภาษาเป็น `List<LangInfoData>` เพื่อให้โมดูลอื่น ๆ ใช้สอบถามการแมปรหัสภาษา

ดูคำอธิบายฟิลด์การกำหนดค่าโดยละเอียดได้ในส่วนที่ 5

### ระยะที่ 2: การซิงโครไนซ์คำแปลอ้างอิง (ขั้นตอนที่ 2-3)

ก่อนเริ่มการแปลหลัก ไปป์ไลน์จะซิงโครไนซ์ข้อมูล **คำแปลอ้างอิง** (Reference Translation) ก่อน

**คำแปลอ้างอิงคืออะไร?** คำแปลอ้างอิงคือม็อดภาษาแปลคุณภาพสูงที่แปลโดยชุมชนด้วยมือ คำแปลเหล่านี้มีความถูกต้องและใช้ศัพท์ที่เป็นเอกภาพ ซึ่งเป็นทรัพยากรทางภาษาที่มีค่า ไปป์ไลน์ไม่ได้ใช้ข้อความจากคำแปลอ้างอิงเป็นผลลัพธ์สุดท้ายโดยตรง (ซึ่งจะละเมิดสิทธิ์ของผู้สร้างต้นฉบับ) แต่ใช้เป็นคลังความรู้สำหรับ RAG (การสร้างเสริมด้วยการค้นคืน) — เมื่อ LLM แปลข้อความใด ไปป์ไลน์จะค้นหาคำแปลที่คล้ายคลึงทางความหมายจากคลังคำแปลอ้างอิงเพื่อใช้เป็น "ตัวอย่างอ้างอิง" ช่วยให้ LLM เข้าใจบริบทและรักษาความเป็นเอกภาพของศัพท์ ส่งผลให้ได้คำแปลคุณภาพสูงขึ้น

ขั้นตอนเฉพาะในระยะนี้:

1. **โหลดแคช**: `RepoDataLoader` โหลดข้อมูลอ้างอิงที่บันทึกจากการรันครั้งก่อนจาก `translation_ref/` รวมถึงข้อมูลเมตาของม็อด รายการคำแปลที่แยกได้ และเวกเตอร์ฝัง แคชเหล่านี้ช่วยหลีกเลี่ยงการดาวน์โหลดและแยกวิเคราะห์ม็อดอ้างอิงทั้งหมดใหม่ทุกครั้ง
2. **ซิงโครไนซ์ข้อมูลเมตาจาก Steam**: `ModInfoFetcher` สอบถาม Steam Web API เพื่อหาข้อมูลล่าสุดของแต่ละม็อดอ้างอิง (โดยเฉพาะฟิลด์ `time_updated`) เปรียบเทียบกับ `timeModUpdated` ในแคช เพื่อระบุม็อดที่มีการเปลี่ยนแปลงเนื้อหา (`needsUpdate = true`)
3. **อัปเดตแบบเพิ่มหน่วย**: ดำเนินการ "ดาวน์โหลด → แยกข้อความ → คำนวณเวกเตอร์ฝัง" เฉพาะกับม็อดอ้างอิงที่ถูกทำเครื่องหมายว่า `needsUpdate` ส่วนม็อดที่ไม่เปลี่ยนแปลงจะใช้แคชเดิม ช่วยประหยัดเวลาและแบนด์วิดท์อย่างมาก
4. **เขียนกลับแบบถาวร**: `ResultWriter.WriteRefDataAsync()` เขียนข้อมูลอ้างอิงที่อัปเดตกลับไปยัง `translation_ref/` เพื่อใช้ในการรันครั้งถัดไป

### ระยะที่ 3: การแปลหลัก (ขั้นตอนที่ 4-14)

นี่คือระยะหลักของไปป์ไลน์ ซึ่งดำเนินการตั้งแต่ "การค้นพบม็อด" ไปจนถึง "การสร้างคำแปล" หลังจากซิงโครไนซ์คำแปลอ้างอิงเสร็จ ไปป์ไลน์ก็มีคลังข้อความอ้างอิงคุณภาพสูงแล้ว จากนั้นจะประมวลผลม็อดทั่วไปทั้งหมดที่ต้องแปลด้วยกระบวนการเดียวกัน และใช้คลังข้อความอ้างอิงเหล่านี้อย่างเต็มที่ในขั้นตอนการแปลสุดท้าย

| ขั้นตอน | โมดูล | หน้าที่ |
|---------|-------|---------|
| 4 | RepoDataLoader | โหลดข้อมูลแคชจากไดเรกทอรี `data/` (ข้อมูลเมตาม็อด คำแปลที่มีอยู่ เวกเตอร์ฝัง) เพื่อเรียกคืนสถานะจากการรันครั้งก่อน |
| 5 | ModIdCollector | รวบรวมรหัส Mod ที่ต้องแปลทั้งหมดจากแพลตฟอร์มชุมชน AsOne และ `request_for_translation.txt` ในเครื่อง รวมและตัดซ้ำ |
| 6 | ModInfoFetcher | สอบถามข้อมูลเมตาล่าสุดของแต่ละม็อดผ่าน Steam Web API (ชื่อ ผู้แต่ง เวลาอัปเดต ฯลฯ) แบบเป็นชุด |
| 7 | ModDownloader | ใช้เครื่องมือ steamcmd ดาวน์โหลดไฟล์ Workshop ม็อดเป็นชุด ๆ ไปยังไดเรกทอรีชั่วคราวในเครื่อง |

| 9 | — | 📊 **เปรียบเทียบความแตกต่าง**: เปรียบเทียบรายการที่แยกได้ใหม่กับแคชทีละรายการ ระบุรายการที่เพิ่มใหม่ แก้ไข และไม่เปลี่ยนแปลง เฉพาะสองประเภทแรกเท่านั้นที่เข้าสู่กระบวนการแปลต่อไป |

| 11 | EmbeddingFetcher | เรียกบริการฝังเวกเตอร์ระยะไกลเพื่อสร้างเวกเตอร์ฝังสำหรับข้อความที่ต้องแปลแต่ละรายการ (384 มิติ) สำหรับการค้นคืนความคล้ายคลึงทางความหมายในภายหลัง |

| 13 | RagContextRetriever | สำหรับแต่ละรายการที่ต้องแปล ค้นหาคำแปลที่มีอยู่แล้วซึ่งคล้ายคลึงทางความหมายมากที่สุดในคลังคำแปลอ้างอิง เพื่อใช้เป็นบริบทอ้างอิงในการแปลด้วย LLM |
| 14 | LLMTranslator | เรียก API โมเดลภาษาขนาดใหญ่เพื่อดำเนินการแปล ประกอบด้วยการวอร์มอัพล่วงหน้า (warmup) และการควบคุมการทำงานพร้อมกันแบบไดนามิก เป็นโมดูลที่ซับซ้อนที่สุดในไปป์ไลน์ |

## 3. หลักการและรายละเอียดทางเทคนิคของแต่ละโมดูล

### 3.1 ConfigReader (`ConfigReaderService`)

**หน้าที่**: โหลดและตรวจสอบไฟล์กำหนดค่าทั้งหมด เป็นโมดูลทางเข้าของไปป์ไลน์ทั้งหมด

`ConfigReader` เป็นโมดูลแรกที่ทำงานหลังจากไปป์ไลน์เริ่มต้น หน้าที่หลักคืออ่านไฟล์กำหนดค่าทั้งหมดในไดเรกทอรี `config/` แปลงเป็นออบเจ็กต์ `PipelineConfig` ที่มีชนิดข้อมูลชัดเจน และทำการตรวจสอบความสมบูรณ์หลังจากโหลดเสร็จ

งานเฉพาะประกอบด้วย:

- **แยกวิเคราะห์การกำหนดค่าหลัก**: อ่าน `config/config.json` แปลงเป็นออบเจ็กต์ `PipelineConfig` ออบเจ็กต์นี้ประกอบด้วยพารามิเตอร์ LLM กลยุทธ์การทำงานพร้อมกัน ค่าเกณฑ์ RAG พารามิเตอร์ Steam API และการตั้งค่าต่าง ๆ ขณะรันทั้งหมด
- **แยกวิเคราะห์คีย์ลับ**: อ่าน `config/secrets.json` ดึง LLM API Key, Steam Web API Key, คีย์และที่อยู่บริการฝังเวกเตอร์
- **การตรวจสอบที่สำคัญ**: ตรวจสอบว่าฟิลด์บังคับสามฟิลด์ ได้แก่ `LLM_KEY`, `STEAM_KEY`, `EMBEDDING_KEY` ไม่ว่างเปล่า หากฟิลด์ใดว่างเปล่าจะข้อยกเว้นและยุติไปป์ไลน์ คีย์ลับสามารถรับได้จาก `secrets.json` หรือตัวแปรสภาพแวดล้อม (ตัวแปรสภาพแวดล้อมมีลำดับความสำคัญสูงกว่า)
- **แยกวิเคราะห์รายการภาษา**: อ่าน `config/supported_languages.json` สร้าง `List<LangInfoData>` รายการนี้กำหนดภาษาปลายทางทั้งหมดที่ไปป์ไลน์ต้องประมวลผล (ทั้งหมด 27 ภาษา) โมดูลต่อ ๆ ไป เช่น การแปล การส่งออก และการรายงาน ต่างก็พึ่งพารายการนี้
- **แยกวิเคราะห์รายการม็อดอ้างอิง**: อ่าน `config/ref_translation_mods.json` เพื่อรับรายการม็อดภาษาแปลอ้างอิงที่ใช้เป็นคลังข้อความ RAG
- **เริ่มต้นไดเรกทอรีชั่วคราว**: สร้างโครงสร้างไดเรกทอรีชั่วคราวที่จำเป็นสำหรับการรันนี้ (เช่น `runTempDir` สำหรับเก็บไฟล์ระหว่างดำเนินการ `downloadedModsTempDir` สำหรับเก็บไฟล์ม็อดที่ดาวน์โหลด) เพื่อให้โมดูลต่อไปมีที่เขียนข้อมูล

ดูคำอธิบายฟิลด์การกำหนดค่าโดยละเอียดได้ในส่วนที่ 5

### 3.2 RepoDataLoader (`RepoDataLoaderService`)

**หน้าที่**: จัดการการโหลด เปรียบเทียบ และบำรุงรักษาสถานะของข้อมูลแคชในเครื่องทั้งหมด

`RepoDataLoader` คือ "ระบบหน่วยความจำ" ของไปป์ไลน์ ทุกครั้งที่ไปป์ไลน์ทำงาน จะโหลดข้อมูลทั้งหมดที่บันทึกจากการรันครั้งก่อนจากระบบไฟล์ในเครื่อง (แคชคำแปล เวกเตอร์ฝัง ข้อมูลเมตาม็อด ฯลฯ) ทำให้ไปป์ไลน์สามารถระบุได้ว่าเนื้อหาใดใหม่ ใดที่ประมวลผลแล้ว และใดที่มีการเปลี่ยนแปลง หากไม่มีโมดูลนี้ ไปป์ไลน์จะต้องประมวลผลม็อดทั้งหมดตั้งแต่ต้นทุกครั้ง ซึ่งมีประสิทธิภาพต่ำมาก

**ประเภทข้อมูลที่โหลด**:

| ข้อมูล | ตำแหน่งจัดเก็บ | การใช้งานหลังจากโหลด |
|--------|---------------|----------------------|
| ข้อมูลเมตาม็อด | `data/modinfos.json` | พิจารณาว่าม็อดใดต้องอัปเดต ใดเป็นครั้งแรก |
| แคชคำแปล | `data/translations/<iso>/*.txt` | เติม `TranslationEntry.translationValues` หลีกเลี่ยงการแปลข้อความที่มีอยู่แล้วซ้ำ |
| เวกเตอร์ฝัง | `data/embeddings/*.bin` | ข้อมูลเวกเตอร์ไบนารีที่บีบอัดด้วย Zstd เติม `embeddingValues` หากข้อความไม่เปลี่ยนแปลงสามารถใช้เวกเตอร์เดิมซ้ำได้ |
| ข้อมูลเมตาของรายการ | `data/entry_metadata/*.json` | บันทึกสถานะ เช่น `sourceHash`, `isActive` ของแต่ละรายการ |

**สามเมธอดหลัก**:

- `DiffTranslationEntries()`: เปรียบเทียบรายการที่แยกได้ใหม่กับรายการในแคชทีละรายการ ตาม `sourceHash` (แฮช SHA256 ของข้อความต้นฉบับ) เพื่อระบุว่าแต่ละข้อความเป็นเพิ่มใหม่ (new), แก้ไข (changed) หรือไม่เปลี่ยนแปลง (unchanged) เฉพาะรายการ new และ changed เท่านั้นที่ต้องเข้าสู่กระบวนการคำนวณเวกเตอร์ฝังและการแปลต่อไป ส่วนรายการ unchanged จะใช้แคชเดิม
- `ComputeSourceHash()`: คำนวณแฮช SHA256 ของข้อความต้นฉบับเพื่อใช้เป็น "ลายนิ้วมือ" ของเนื้อหา ความน่าจะเป็นของการชนกันของแฮชต่ำมาก สามารถใช้ตรวจจับการเปลี่ยนแปลงได้อย่างน่าเชื่อถือ
- `MarkMissingFreshEntriesInactive()`: หากรายการเก่าในแคชไม่พบในผลการแยกใหม่ (แสดงว่าผู้สร้างม็อดลบข้อความนี้) จะทำเครื่องหมาย `isActive = false` เก็บประวัติไว้แต่ไม่นำไปใช้ในการแปลอีก

### 3.3 ModIdCollector (`ModIdCollectorService`)

**หน้าที่**: รวบรวมรหัส Steam Workshop Mod ที่ต้องแปลทั้งหมดจากหลายแหล่ง รวมและตัดซ้ำเป็นรายการที่พร้อมประมวลผลแบบรวมศูนย์

ไปป์ไลน์ต้องรู้ว่า "ม็อดใดบ้างที่ต้องแปล" ข้อมูลนี้มาจากสองช่องทาง:

**แหล่งที่ 1 — รายการระยะไกลจากชุมชน AsOne**:

[AsOne](https://www.asone.fun/) คือแพลตฟอร์มการแปลของกลุ่มแปลภาษา Project Zomboid จีน ซึ่งดูแลรายการม็อดสาธารณะ ไปป์ไลน์ส่งคำขอ HTTP GET ไปยัง API (`api/Home/GetAllModinfo`) เพื่อรับรหัสม็อดที่ลงทะเบียนทั้งหมด คำขอส่งแบบไม่ระบุตัวตน หากหมดเวลาติดต่อกัน 3 ครั้งจะข้ามรายการระยะไกลนี้

**แหล่งที่ 2 — ไฟล์คำขอแปลในเครื่อง**:

`config/request_for_translation.txt` คือไฟล์รายการรหัสม็อดที่ดูแลด้วยมือ แต่ละบรรทัดมี Workshop ID เป็นตัวเลขล้วน ๆ บรรทัดที่ขึ้นต้นด้วย `#` คือข้อคิดเห็น บรรทัดว่างจะถูกข้ามอัตโนมัติ ไฟล์นี้ใช้เสริมม็อดที่ไม่อยู่ในรายการ AsOne แต่ชุมชนมีความต้องการแปล

**กลยุทธ์การรวม**: เมื่อรวมรายการ ID จากสองแหล่ง รายการระยะไกลจาก AsOne จะเป็นหลัก ID ในไฟล์คำขอในเครื่องที่ไม่อยู่ในรายการระยะไกลจะถูกเพิ่มเป็นส่วนเสริม ID ที่มีอยู่แล้วจะไม่ถูกเพิ่มซ้ำ สุดท้ายจะส่งออกรายการ ID ที่สมบูรณ์และตัดซ้ำแล้ว

### 3.4 ModInfoFetcher (`ModInfoFetcherService`)

**หน้าที่**: สอบถามข้อมูลเมตาโดยละเอียดของม็อดแบบเป็นชุดผ่าน Steam Web API เพื่อพิจารณาว่าม็อดใดต้องอัปเดต

หลังจากได้รายการรหัสม็อดแล้ว ไปป์ไลน์ต้องรู้ข้อมูลพื้นฐานของแต่ละม็อด — ชื่อ ผู้แต่ง เวลาอัปเดตล่าสุด ฯลฯ ข้อมูลเหล่านี้ได้จากอินเทอร์เฟซ `ISteamRemoteStorage/GetPublishedFileDetails/v1/` อย่างเป็นทางการของ Steam

**รายละเอียดการทำงาน**:

- **การแบ่งคำขอเป็นชุด**: Steam API มีข้อจำกัดด้านจำนวนต่อการเรียก ดังนั้นไปป์ไลน์จะส่งคำขอเป็นชุดตาม `steamApiChunkSize` (ค่าเริ่มต้น 100) โดยมีระยะห่างระหว่างชุดเพื่อหลีกเลี่ยงการถูกจำกัดอัตรา
- **กลไกความทนทานต่อข้อผิดพลาด**: หาก 5 ชุดติดต่อกันล้มเหลวทั้งหมด (อาจเป็นปัญหาด้านเครือข่ายหรือ API ไม่พร้อมใช้งานชั่วคราว) ไปป์ไลน์จะหยุดสอบถามและเก็บข้อมูลส่วนที่สำเร็จไว้ แทนที่จะทิ้งผลลัพธ์ทั้งหมด
- **การแมปฟิลด์สำคัญ**:
  - `consumer_app_id`: ตรวจสอบว่ารายการนี้เป็นของ Project Zomboid หรือไม่ (App ID = `108600`) ม็อดที่ไม่ใช่ PZ จะถูกทำเครื่องหมาย `isAvailable = false` และข้ามการดาวน์โหลดในภายหลัง
  - `time_updated`: เวลาอัปเดตล่าสุดที่ Steam บันทึก เปรียบเทียบกับ `timeModUpdated` ในแคช หากอันแรกใหม่กว่า จะทำเครื่องหมาย `needsUpdate = true` แสดงว่าเนื้อหาม็อดอาจมีการเปลี่ยนแปลง ต้องแยกและแปลใหม่
  - `title` → แมปเป็น `modName` (ชื่อม็อด)
  - `creator` → รับชื่อผู้สร้างผ่านอินเทอร์เฟซผู้ใช้ Steam

### 3.5 ModDownloader (`ModDownloaderService`)

**หน้าที่**: ใช้เครื่องมือบรรทัดคำสั่ง steamcmd ดาวน์โหลดไฟล์ม็อดจาก Steam Workshop

[steamcmd](https://developer.valvesoftware.com/wiki/SteamCMD) คือไคลเอนต์ Steam รูปแบบบรรทัดคำสั่งที่ Valve จัดทำขึ้น รองรับการเข้าสู่ระบบแบบไม่ระบุตัวตนและดาวน์โหลดเนื้อหา Workshop ไปป์ไลน์เรียกใช้ steamcmd เพื่อดาวน์โหลดไฟล์ม็อดแบบเป็นชุด

**ขั้นตอนการดาวน์โหลด**:

1. **คัดลอก steamcmd**: คัดลอก `src/3rd_party/steamcmd/` ไปยังไดเรกทอรีชั่วคราวเฉพาะของแต่ละชุด เนื่องจากแต่ละชุดการดาวน์โหลดจะเริ่มต้นกระบวนการ steamcmd ของตนเอง หากหลายกระบวนการใช้ไฟล์เดียวกันอาจเกิดความขัดแย้ง
2. **รันคำสั่งดาวน์โหลด**: รัน `steamcmd +login anonymous +workshop_download_item 108600 <modId> +quit` โดย `108600` คือ App ID ของ Project Zomboid และ `anonymous` หมายถึงเข้าสู่ระบบแบบไม่ระบุตัวตน (การดาวน์โหลด Workshop ไม่ต้องการบัญชี)
3. **ตรวจสอบผลลัพธ์**: แยกวิเคราะห์บันทึกผลลัพธ์ของ steamcmd เพื่อยืนยันว่าการดาวน์โหลดสำเร็จหรือไม่ หากล้มเหลว ให้ลองใหม่ตามจำนวนครั้งที่กำหนด (`steamMaxRetries + 1`)
4. **ดาวน์โหลดต่อเนื่อง**: ม็อดที่ดาวน์โหลดสำเร็จแล้วจะข้ามไปโดยอัตโนมัติ ไม่มีการดาวน์โหลดซ้ำ

**รายละเอียดการจัดการกระบวนการ**:

- ใช้ `ConcurrentDictionary` ทั่วโลกเพื่อติดตามกระบวนการ steamcmd ที่กำลังทำงานทั้งหมด
- ลงทะเบียน callback สำหรับ `Ctrl+C` และ `ProcessExit` เพื่อให้แน่ใจว่าเมื่อไปป์ไลน์ถูกหยุดด้วยมือหรือออกผิดปกติ จะสามารถล้างกระบวนการย่อยทั้งหมด (`Kill(entireProcessTree: true)`) ป้องกันไม่ให้มีกระบวนการซอมบี้หลงเหลือ
- กระบวนการ steamcmd รอการสิ้นสุดแบบอะซิงโครนัสด้วย `WaitForExitAsync()` โดยไม่ตั้งเวลาหมด — หากกระบวนการค้าง ต้องใช้ callback ข้างต้นเพื่อยุติไปป์ไลน์ด้วยมือเพื่อทำความสะอาด

### 3.6 ContentExtractor (`ContentExtractorService`)

**หน้าที่**: แยกวิเคราะห์และแยกข้อความที่แปลได้ทั้งหมดจากไฟล์ม็อดที่ดาวน์โหลด เป็นขั้นตอนสำคัญในการ "ทำความเข้าใจม็อด" ของไปป์ไลน์

ม็อดของ Project Zomboid เก็บข้อความแปลไว้ในไดเรกทอรีเฉพาะ `ContentExtractor` จะวนซ้ำไดเรกทอรีเหล่านี้ แยกวิเคราะห์ไฟล์ TXT (รูปแบบ Lua) และ JSON เพื่อดึงคู่ "ต้นฉบับ → คำแปล" แต่ละรายการ

**เส้นทางที่สแกน**:

```
<mod_root>/**/Translate/<game_code>/*.txt|*.json
```

กล่าวคือ ที่ความลึกใด ๆ ภายใต้ไดเรกทอรีรากของม็อด ให้ค้นหาไฟล์ `.txt` หรือ `.json` ในโฟลเดอร์ `Translate/<รหัสภาษา>/`

**การแมปรหัสภาษา** (รหัสในเกม → รหัสมาตรฐาน ISO):

| รหัสเกม | ISO | ภาษา |
|---------|-----|------|
| CN | zh-hans | จีนตัวย่อ |
| CH | zh-hant | จีนตัวเต็ม |
| EN | en | อังกฤษ |
| JP | ja | ญี่ปุ่น |
| ... | ... | ... |

**การแยกวิเคราะห์ TXT (รูปแบบ Lua ของ PZ)**:

ไฟล์คำแปลแบบดั้งเดิมของ PZ ใช้รูปแบบคล้าย Lua table ขั้นตอนการแยกวิเคราะห์:

1. **กรองไฟล์ที่ไม่ใช่คำแปล**: ข้ามไฟล์ข้อมูลเมตา เช่น `TranslationNotes`, `TranslationBy`, `Code - TXT`, `Credits`, `Language` เนื่องจากไม่มีเนื้อหาคำแปลจริง
2. **ระบุคีย์หลัก (masterKey)**: ใช้นิพจน์ปกติจับคู่การประกาศบล็อก เช่น `UI_NewCharScreen = {` เพื่อแยก masterKey masterKey คือส่วนแรกของคีย์แปล สอดคล้องกับชื่อโมดูล UI ในเกม PZ
3. **แยกวิเคราะห์ทีละบรรทัด**: ภายในแต่ละบล็อก masterKey ให้แยกวิเคราะห์คำแปลแต่ละรายการในรูปแบบ `key = "value"` คีย์แปลที่สมบูรณ์ประกอบด้วย `masterKey_key` (เช่น `UI_NewCharScreen_Start`)
4. **การต่อสตริง**: ไฟล์ Lua ของ PZ รองรับตัวดำเนินการ `..` สำหรับการต่อสตริง (เช่น `"Hello " .. "World"`) ตัวแยกวิเคราะห์จะคำนวณผลลัพธ์การต่อ
5. **รองรับรูปแบบ JSON**: ม็อดบางตัวใช้รูปแบบ JSON แบบ `"key": "value"` ในไฟล์ TXT ตัวแยกวิเคราะห์รองรับเช่นกัน
6. **การจัดการข้อยกเว้น**: บรรทัดที่ไม่สามารถแยกวิเคราะห์ได้จะถูกเขียนลงในไฟล์บันทึก `fuck.txt` เพื่อให้ตรวจสอบและแก้ไขข้อบกพร่องของตัวแยกวิเคราะห์ด้วยตนเอง

**การแยกวิเคราะห์ JSON**:

PZ เวอร์ชันใหม่ (Build 42+) รองรับไฟล์คำแปลรูปแบบ JSON ตัวแยกวิเคราะห์จะขยายออบเจ็กต์ JSON ที่ซ้อนกันแบบเรียกซ้ำ ทำให้เป็นคู่ key-value แบบราบ และรองรับไวยากรณ์ JSON ที่ไม่เป็นมาตรฐาน เช่น จุลภาคท้ายรายการและความคิดเห็น เพื่อรับมือกับรูปแบบต่าง ๆ ของผู้สร้างม็อด

**กฎการรวม**:

เมื่อคีย์แปลเดียวกันปรากฏในหลายไฟล์ (เช่น ม็อดเดียวกันมีไฟล์คำแปลสำหรับเวอร์ชัน 42 และ 42.19 พร้อมกัน) ต้องตัดสินใจว่าจะเก็บไฟล์ใด กฎมีดังนี้:

- **ลำดับความสำคัญของรูปแบบ**: JSON ครอบคลุม TXT เนื่องจาก JSON เป็นรูปแบบมาตรฐานใหม่ของ PZ และควรนำมาใช้ก่อน ภายในใช้ enum `SourceKind` แยกแยะ (JSON = 1, TXT = 0)
- **ลำดับความสำคัญของเวอร์ชัน**: ในรูปแบบเดียวกัน ให้เก็บไฟล์ที่มีเวอร์ชันเกมสูงสุด กฎการแยกวิเคราะห์เวอร์ชันดูด้านล่าง
- **บันทึกครบถ้วน**: ฟิลด์ `containingFileInfos` จะบันทึกข้อมูลไฟล์ต้นฉบับทั้งหมด (รวมที่ถูกทิ้ง) เพื่อให้สามารถตรวจสอบย้อนกลับได้

**กฎการแยกวิเคราะห์เวอร์ชัน**:

```
ไม่มีเวอร์ชัน → 0.0
common   → 1.0
42       → 42.0
42.19    → 42.19
```

### 3.7 ContentChecker (`ContentCheckerService`)

**หน้าที่**: ตรวจสอบความปลอดภัยของข้อความม็อดก่อนการแปล เพื่อกรองม็อดที่มีเนื้อหาละเมิด

ไปป์ไลน์การแปลอัตโนมัติต้องจัดการกับเนื้อหาม็อดจากอินเทอร์เน็ตโดยพลการ ซึ่งอาจมีข้อความที่ละเมิดข้อกำหนดของแพลตฟอร์มหรือกฎหมาย `ContentChecker` ใช้ LLM ตรวจสอบเนื้อหาม็อดโดยอัตโนมัติ เพื่อให้แน่ใจว่าคำแปลที่ไปป์ไลน์ส่งออกไม่มีเนื้อหาที่ละเมิด

**มิติการตรวจสอบ** (เส้นแดงสามประเภท):

| ประเภท | เกณฑ์การตัดสิน |
|--------|---------------|
| **ยาเสพติด** | การบรรยายการเสพ การฉีด การผลิต การซื้อขายยาเสพติด; การทำให้พฤติกรรมเสพติดดูดีหรือชักนำ; การอุปมาอุปไมยด้วยวิธีเสมือนจริงถึงยาเสพติดจริง |
| **พฤติกรรมทางเพศกับเด็ก** | เนื้อหาที่มีนัยทางเพศต่อผู้เยาว์อายุต่ำกว่า 14 ปี |
| **การข่มขืน** | การบรรยายหรือทำให้พฤติกรรมทางเพศที่ไม่สมัครใจดูดี รวมถึงการข่มขู่ด้วยความรุนแรง การใช้ยาสลบ ฯลฯ |

**กลไกการตรวจสอบ**:

- **กลยุทธ์การสุ่มตัวอย่าง**: สุ่มข้อความต้นฉบับสูงสุด 1,000 รายการต่อม็อดเป็นตัวอย่างตรวจสอบ จำนวนอักขระทั้งหมดของตัวอย่างต้องไม่เกิน 60,000 เพื่อให้ครอบคลุมเนื้อหาหลักของม็อดโดยไม่เกินหน้าต่างบริบทของ LLM
- **การตัดข้อความ**: ข้อความเดี่ยวที่ยาวเกิน 1,600 อักขระจะถูกตัดให้เหลือ 1,600 อักขระแรกสำหรับการตรวจสอบ ข้อความที่ยาวมากมักเป็นข้อมูลการกำหนดค่ามากกว่าภาษาธรรมชาติ การตัดไม่ส่งผลต่อการตัดสิน
- **การตรวจสอบด้วย LLM**: เรียกใช้โมเดล `deepseek-v4-flash` โดยใช้ JSON Mode เพื่อส่งออกผลการตรวจสอบแบบมีโครงสร้าง (พร้อมผลการตัดสินและระดับความเชื่อมั่น)
- **กลยุทธ์แคช**: ผลการตรวจสอบจะถูกแคช 90 วัน (ควบคุมโดย `contentCheckIntervalDays`) ภายในระยะเวลาแคชที่ยังมีผล ม็อดเดียวกันจะไม่ถูกตรวจสอบซ้ำ
- **การเปลี่ยนสถานะ**: `UNKNOWN → NEEDVERIFICATION → ACCEPTED / REJECTED`

**กลไกการตรวจสอบด้วยมนุษย์**: เมื่อระดับความเชื่อมั่นที่ LLM ส่งออกต่ำกว่า 0.7 ผลการตรวจสอบนั้นถือว่าเชื่อถือได้ไม่เพียงพอ สถานะม็อดจะคงอยู่ที่ `NEEDVERIFICATION` รอการตัดสินโดยมนุษย์ เพื่อป้องกันไม่ให้ม็อดปกติถูกกรองอย่างผิดพลาดเนื่องจากการตัดสินผิดของ LLM

### 3.8 EmbeddingFetcher (`EmbeddingFetcherService`)

**หน้าที่**: เรียกบริการฝังเวกเตอร์ระยะไกลเพื่อสร้างเวกเตอร์ฝัง (Embedding) สำหรับข้อความที่ต้องแปลแต่ละรายการ เพื่อใช้ในการค้นคืนแบบ RAG

เวกเตอร์ฝังคือเครื่องมือทางคณิตศาสตร์ใน NLP สมัยใหม่ที่ใช้แทนความหมายของข้อความ — ข้อความที่มีความหมายใกล้เคียงกันจะมีเวกเตอร์อยู่ใกล้กันในปริภูมิ เวกเตอร์ฝังใช้เพื่อ "ค้นหาคำแปลอ้างอิงที่มีความหมายใกล้เคียงกับข้อความที่ต้องแปลมากที่สุด" ซึ่งเป็นฟังก์ชันหลัก

**ทำไมต้องใช้บริการระยะไกล?** แม้ว่าโมเดลฝัง (เช่น `bge-small-en-v1.5`) จะมีขนาดไม่ใหญ่ แต่การรันในเครื่องยังคงต้องโหลดน้ำหนักโมเดลเข้าสู่หน่วยความจำ เมื่อพิจารณาข้อจำกัดด้านหน่วยความจำของ GitHub Actions runner (โดยปกติ 7GB) และไปป์ไลน์เองก็ต้องใช้หน่วยความจำจำนวนมากสำหรับงานแปล การย้ายการคำนวณฝังไปยังบริการระยะไกลเฉพาะจึงเป็นทางเลือกที่เหมาะสมกว่า

**โปรโตคอลการสื่อสาร**:

บริการฝังใช้รูปแบบการตรวจสอบสิทธิ์แบบไร้สถานะน้ำหนักเบา:
1. **UDP Knock**: ส่งแพ็กเก็ต UDP ไปยังบริการเป็นสัญญาณเริ่มต้น
2. **การเข้ารหัส AES-256-GCM**: การสื่อสาร HTTP ในภายหลังใช้การเข้ารหัส AES-256-GCM โดยคีย์ได้มาจาก `EMBEDDING_KEY` ใน `secrets.json` ผ่าน SHA256
3. **HTTP POST**: การส่งข้อมูลจริงทำผ่าน HTTP POST

การออกแบบนี้หลีกเลี่ยงความเสี่ยงของการส่ง API Key ใน HTTP Header แบบข้อความธรรมดา ขณะเดียวกันก็รักษาความไร้สถานะของฝั่งบริการ

**พารามิเตอร์ทางเทคนิค**:

| พารามิเตอร์ | ค่า | คำอธิบาย |
|------------|-----|----------|
| โมเดลฝัง | `bge-small-en-v1.5` | โมเดลฝังภาษาอังกฤษน้ำหนักเบาที่ BAAI เผยแพร่ |
| มิติเวกเตอร์ | 384 | ข้อความแต่ละรายการแมปเป็นตัวเลข float32 จำนวน 384 ตัว |
| การตัดอินพุต | 500 UTF-8 characters | ข้อความที่ยาวกว่านี้จะถูกตัดก่อนส่งเข้าโมเดล |
| ขนาดชุด | 32 | ส่งข้อความ 32 รายการต่อคำขอ สร้างสมดุลระหว่างปริมาณงานและความหน่วง |
| รูปแบบจัดเก็บ | ไบนารีบีบอัด Zstd | อัตราส่วนการบีบอัดประมาณ 4:1 ประหยัดพื้นที่ดิสก์อย่างมีนัยสำคัญ |

**ขั้นตอนการประมวลผล**:

1. **รวบรวมตัวเลือก** (`BuildCandidates`): รวบรวมรายการที่ขาดเวกเตอร์ฝังทั้งหมด รวมถึงรายการเพิ่มใหม่/แก้ไขที่พบในการรันนี้ (diff), รายการคำแปลอ้างอิง และรายการประวัติที่ต้อง backfill
2. **ตัดซ้ำด้วยแฮช**: ข้อความที่มีเนื้อหาเหมือนกันจะต้องมีแฮชเหมือนกัน ในกรณีนี้สามารถใช้เวกเตอร์ฝังที่มีอยู่เดิมซ้ำได้ หลีกเลี่ยงการคำนวณซ้ำ
3. **ส่งเป็นชุด**: แพ็กรายการที่เลือกเป็นชุดละ 32 รายการ ส่งไปยังบริการฝังทีละชุด หากล้มเหลวติดต่อกัน ≥3 ชุดจะยุติขั้นตอนการฝัง
4. **จัดเก็บแบบถาวร**: เวกเตอร์ที่ได้รับจะถูกเขียนในรูปแบบ Zstd ไปยัง `data/embeddings/<modId>.bin`

**กลไก Backfill**: เมื่อไปป์ไลน์รองรับภาษาใหม่เป็นครั้งแรก อาจมีรายการจำนวนมากในแคชประวัติที่ขาดเวกเตอร์ฝังสำหรับภาษานั้น หากคำนวณฝังให้ทั้งหมดในครั้งเดียว จะสร้างภาระแก่บริการมากและใช้เวลานาน กลไก Backfill จำกัดจำนวนการฝังที่ขาดหายไปที่จะคำนวณต่อการรันสูงสุด 10,000,000 รายการ กระจายงานไปยังหลายการรันเพื่อค่อย ๆ ทำให้สมบูรณ์

### 3.9 TranslationBatcher (`TranslationBatcherService`)

**หน้าที่**: จัดกลุ่มรายการที่ต้องแปลตามม็อดและงบประมาณโทเค็นเป็นชุดการแปล (`TranslationBatch`) ซึ่งเป็นหน่วยพื้นฐานสำหรับการแปลด้วย LLM

การแปลทีละรายการโดยตรงไม่มีประสิทธิภาพ — ความหน่วงของเครือข่ายต่อการเรียก API แต่ละครั้งมากกว่าเวลาในการอนุมานของโมเดล `TranslationBatcher` จะแพ็กรายการข้อความที่ต้องแปลหลายรายการเป็นชุด ทำให้แต่ละการเรียก API สามารถประมวลผลข้อความหลายรายการ เพิ่มปริมาณงานอย่างมีนัยสำคัญ

**กลยุทธ์การแพ็ก**:

1. **การจัดเรียงตามลำดับความสำคัญ**: ม็อดเรียงตามลำดับความสำคัญจากมากไปน้อย ลำดับความสำคัญคำนวณจากจำนวนการสมัครรับ (subscription) และจำนวนการถูกใจ (favorite) — ม็อดที่ได้รับความนิยมมากกว่าจะได้รับการแปลก่อน
2. **ข้อจำกัดสองประการ**: แต่ละชุดอยู่ภายใต้ข้อจำกัดสองประการพร้อมกัน:
   - `batch_size` (จำนวนรายการสูงสุด ค่าเริ่มต้น 30): ชุดหนึ่งมีรายการแปลได้สูงสุด 30 รายการ
   - `batch_token_budget` (งบประมาณโทเค็น ค่าเริ่มต้น 2000): จำนวนโทเค็นรวมของข้อความอินพุตในชุดต้องไม่เกิน 2000 แม้ว่าจำนวนรายการจะไม่ถึงขีดจำกัด หากงบประมาณโทเค็นหมดก็จะตัดชุด
3. **การจัดกลุ่มตามม็อดเดียวกัน**: รายการของม็อดเดียวกันจะถูกแพ็กให้อยู่ในชุดเดียวกันมากที่สุด ซึ่งช่วยให้ LLM เข้าใจความสม่ำเสมอของศัพท์ภายในม็อดเดียวกัน หลีกเลี่ยงการแตกกระจายของบริบท
4. **การทำเครื่องหมายภาษา**: `TranslationBatch` แต่ละชุดมีฟิลด์ `targetLang` ระบุภาษาปลายทางของชุด รายการที่มีภาษาปลายทางต่างกันจะไม่ถูกผสมในชุดเดียวกัน

**วิธีการประมาณโทเค็น**: เนื่องจากไปป์ไลน์ไม่พึ่งพาไลบรารี tokenizer เฉพาะ (เพื่อหลีกเลี่ยงการเพิ่มการพึ่งพาโดยไม่จำเป็น) จึงใช้วิธีการประมาณแบบง่าย — แบ่งข้อความภาษาอังกฤษตามช่องว่างและเครื่องหมายวรรคตอนเพื่อประมาณจำนวนโทเค็นคร่าว ๆ ค่านี้ใช้สำหรับการควบคุมงบประมาณ ไม่ต้องการความแม่นยำสัมบูรณ์

**เจตนาการออกแบบ — การจัดกลุ่มตามม็อดเดียวกัน**: การจัดกลุ่มรายการของม็อดเดียวกันให้อยู่ในชุดเดียวกันมากที่สุด แทนที่จะผสมข้ามม็อดเพื่อเพิ่มอัตราการเติมชุด เนื่องจาก LLM จะใช้ข้อมูลบริบทภายในชุดเดียวกันเพื่อรักษาความสม่ำเสมอของศัพท์ระหว่างการแปล — ข้อความของม็อดเดียวกันใช้ระบบศัพท์และรูปแบบการเล่าเรื่องร่วมกัน การแปลด้วยกันช่วยให้ LLM สร้างคำแปลที่มีรูปแบบสอดคล้องกัน

### 3.10 RagContextRetriever (`RagContextRetrieverService`)

**หน้าที่**: ใช้ความคล้ายคลึงของเวกเตอร์ ค้นหาคำแปลที่มีอยู่แล้วซึ่งคล้ายคลึงกับข้อความที่ต้องแปลมากที่สุดจากคลังคำแปลอ้างอิง เพื่อใช้เป็นบริบทอ้างอิงในการแปลด้วย LLM

RAG (Retrieval-Augmented Generation) คือ **การรับประกันคุณภาพหลัก** ของการแปลในไปป์ไลน์นี้ แนวคิดพื้นฐานคือ: ให้ LLM "เห็น" ตัวอย่างประโยคที่แปลโดยมนุษย์ในชุมชนเมื่อแปลแต่ละข้อความ เพื่อเรียนรู้รูปแบบ ศัพท์ และวิธีการแสดงออก

**ขั้นตอนการค้นคืน**:

1. **สร้างดัชนีอ้างอิง** (`BuildReferences`): จากรายการคำแปลอ้างอิงและคำแปลที่มีอยู่ กรองเฉพาะรายการที่ตรงกับทิศทางการแปลปัจจุบัน (เช่น `embeddingKey = "en:zh-hans"` ซึ่งเป็นรายการ "จากอังกฤษไปยังภาษาปลายทาง") โหลดเวกเตอร์ฝังเข้าสู่หน่วยความจำเพื่อใช้เป็นดัชนีค้นคืน
2. **การค้นหาการจับคู่ที่แน่นอน** (`BuildExactReferenceLookup`): สำหรับรายการที่มี translationKey เหมือนกันทุกประการ ให้สร้างการแมปโดยตรง — คีย์เดียวกันหมายถึงข้อความเดียวกัน นี่คือสัญญาณอ้างอิงที่แข็งแกร่งที่สุด
3. **การคำนวณความคล้ายคลึงโคไซน์**: สำหรับเวกเตอร์สอบถาม (query embedding) ของแต่ละข้อความที่ต้องแปล ให้วนซ้ำเวกเตอร์อ้างอิงทั้งหมดในดัชนีอ้างอิง คำนวณความคล้ายคลึงโคไซน์ระหว่างทั้งสอง ความคล้ายคลึงโคไซน์มีค่าในช่วง [-1, 1] ยิ่งใกล้ 1 หมายถึงยิ่งมีความหมายใกล้เคียงกัน
4. **การกรองตามเกณฑ์**: ทิ้งผลการอ้างอิงที่มีความคล้ายคลึงต่ำกว่า `similarity_threshold` (ค่าเริ่มต้น 0.8) เกณฑ์นี้ช่วยให้มั่นใจได้ว่าจะนำเฉพาะคำแปลอ้างอิงที่เกี่ยวข้องในระดับสูงเท่านั้น
5. **การตัด Top-K**: จากตัวเลือกที่ผ่านเกณฑ์ ให้เลือก K รายการที่มีความคล้ายคลึงสูงสุด (ค่าเริ่มต้น 3 รายการ) เพื่อใช้เป็นบริบทอ้างอิงในการแปลด้วย LLM

**การเพิ่มประสิทธิภาพ**: การค้นคืนเกี่ยวข้องกับการดำเนินการ dot product เวกเตอร์จำนวนมาก (384 มิติ × หลักหมื่นรายการอ้างอิง × หลักหมื่นรายการสอบถาม) ซึ่งมีปริมาณการคำนวณมหาศาล ไปป์ไลน์ใช้ `Parallel.For` เพื่อการประมวลผลแบบหลายเธรดขนาน และใช้คำสั่ง SIMD `Vector128` ในลูปชั้นในเพื่อเร่งการดำเนินการ dot product ใช้ความสามารถในการคำนวณเวกเตอร์ของ CPU สมัยใหม่อย่างเต็มที่

**การเชื่อมต่อกับ LLMTranslator**: หลังจากการค้นคืนเสร็จสิ้น คำแปลอ้างอิง Top-K ของแต่ละข้อความที่ต้องแปลจะถูกเขียนลงในฟิลด์บริบท RAG ของแต่ละรายการใน `TranslationBatch` เมื่อ `LLMTranslator` สร้าง Prompt การแปล (ดูหัวข้อ 3.11 `BuildPromptItems`) จะนำคำแปลอ้างอิงเหล่านี้เป็นบริบทใน Prompt เพื่อให้ LLM ใช้อ้างอิง

### 3.11 LLMTranslator (`LLMTranslatorService`)

**หน้าที่**: เรียก API โมเดลภาษาขนาดใหญ่เพื่อดำเนินการแปลจริง เป็นโมดูลที่ซับซ้อนที่สุดในไปป์ไลน์ทั้งหมด

`LLMTranslator` ไม่เพียงรับผิดชอบการสร้าง Prompt และการแยกวิเคราะห์การตอบสนอง แต่ยังรวมถึงกลไกทางวิศวกรรมที่สมบูรณ์ เช่น การวอร์มอัพล่วงหน้า (warmup), การควบคุมการทำงานพร้อมกันแบบไดนามิก, การป้องกันหน่วยความจำ และการลองใหม่เมื่อเกิดข้อผิดพลาด

**สถาปัตยกรรมโดยรวม**:

การแปลแบ่งเป็นสองระยะ — **ระยะเตรียมการ** และ **ระยะดำเนินการ**:

```
PrepareTranslationPlanAsync  → สร้างแผนการแปล (LlmTranslationPlan)
    ├── กรองข้อความว่างเปล่า (เขียน EmptyWrites โดยตรง ไม่ต้องเรียก LLM)
    ├── BuildPromptItems (เพิ่มบริบท RAG และอภิธานศัพท์ให้แต่ละข้อความ)
    ├── BuildPrompt (ต่อ system prompt + กฎการแปล + รายการรายการ)
    └── เมื่อจำนวนชุด >5 ให้สร้าง warmup prompt (ใช้สำหรับการวอร์มอัพล่วงหน้า)

ExecuteTranslationPlansAsync  → ดำเนินการตามแผนการแปลทั้งหมดแบบเรียงลำดับ
    ├── เขียน EmptyWrites (ผลลัพธ์ตัวยึดตำแหน่งสำหรับข้อความว่างเปล่า)
    ├── ExecuteWarmupAsync (ระยะวอร์มอัพ: คำขอเดียวแบบทำงานพร้อมกันต่ำ)
    │   └── AccountFatal → ยุติแผนการแปลที่เหลือทั้งหมด
    ├── ExecuteWorkItemsAsync / ExecuteWorkItemsFixedWindowAsync (ระยะการแปลหลัก)
    └── ApplyTargetWrite (เขียนผลการแปลลงใน entry.translationValues)
```

**การควบคุมการทำงานพร้อมกันแบบไดนามิก** (`ExecuteWorkItemsAsync`):

กลยุทธ์การจำกัดอัตรา (rate limit) ของ DeepSeek API ไม่ได้โปร่งใสอย่างสมบูรณ์ การใช้ค่าคงที่แน่นอนอาจนำไปสู่ปัญหาสองประการ — หากระมัดระวังเกินไปจะทำให้ปริมาณงานไม่พอ หากรุนแรงเกินไปจะทำให้เกิดข้อผิดพลาด 429 ถูกจำกัดอัตรา ด้วยเหตุนี้ไปป์ไลน์จึงใช้อัลกอริทึมควบคุมการทำงานพร้อมกันแบบปรับตัวได้:

```
การทำงานพร้อมกันเริ่มต้น = auto(profile) หรือค่าที่กำหนด
   ↓
ประเมินทุกครั้งที่งานเสร็จ:
    สำเร็จ → successStreak++ (ตัวนับความสำเร็จเพิ่มขึ้น)
    สำเร็จ && streak ≥ min(currentLimit, 100) → ลองเพิ่มการทำงานพร้อมกัน 25%
    ล้มเหลว && มีสัญญาณกดดัน → pressureFailureStreak++
    สัญญาณกดดันติดต่อกัน ≥ 3 → ลดการทำงานพร้อมกันครึ่งหนึ่ง (ลดขนาด)
    AccountFatal (เงินไม่พอ/บัญชีถูกระงับ) → ทำเครื่องหมาย stopScheduling ยุติงานที่เหลือทั้งหมด
```

แนวคิดหลักคือ "เอฟเฟกต์การเขย่งปลายเท้า" — ค่อยๆ ทดสอบขีดจำกัดการทำงานพร้อมกันของ API อย่างค่อยเป็นค่อยไป เมื่อสำเร็จก็ทดสอบเพิ่มขึ้น เมื่อล้มเหลวก็ลดลงอย่างรวดเร็ว

**การตรวจจับโปรไฟล์การทำงานพร้อมกันอัตโนมัติ**:

เมื่อค่า `initial=0` หรือ `maximum=0` ในการกำหนดค่า ไปป์ไลน์จะเลือกพารามิเตอร์การทำงานพร้อมกันที่เหมาะสมโดยอัตโนมัติตามสภาพแวดล้อมการทำงานและชื่อโมเดล **ลำดับความสำคัญของการตรวจจับ**: ตรวจสอบตัวแปรสภาพแวดล้อม `GITHUB_ACTIONS` ก่อน (สภาพแวดล้อม CI บังคับใช้การทำงานพร้อมกันต่ำ) จากนั้นจับคู่ตามชื่อโมเดล:

| เงื่อนไขการตรวจจับ | Initial | Maximum | สถานการณ์ที่ใช้งาน |
|-------------------|---------|---------|-------------------|
| `GITHUB_ACTIONS=true` (ลำดับสูงสุด) | 4 | 32 | ทรัพยากร CI runner (CPU/หน่วยความจำ) มีจำกัด |
| model มี `v4-flash` | 128 | 2000 | DeepSeek V4 Flash ความสามารถการทำงานพร้อมกันสูง |
| model มี `v4-pro` | 64 | 400 | DeepSeek V4 Pro ความสามารถการทำงานพร้อมกันปานกลาง |
| โมเดลอื่น ๆ | 16 | 128 | ค่าเริ่มต้นแบบระมัดระวังสำหรับโมเดลที่ไม่รู้จัก |

**โหมดหน้าต่างคงที่** (`llmFixedConcurrency > 0`):

สำหรับสภาพแวดล้อมที่ทราบขีดจำกัดการทำงานพร้อมกันของ API อย่างชัดเจน สามารถเปิดใช้โหมดหน้าต่างคงที่ โหมดนี้จะจัดกลุ่ม work items เป็นหน้าต่างขนาดคงที่ แต่ละหน้าต่างทำงานแบบพร้อมกันภายใน และเรียงลำดับอย่างเคร่งครัดระหว่างหน้าต่าง พฤติกรรมที่กำหนดได้นี้ช่วยขจัดความไม่แน่นอนของการปรับแบบไดนามิก เหมาะสำหรับการทำงานที่เสถียรในสภาพแวดล้อมการผลิต

**องค์ประกอบของ Prompt การแปล**:

Prompt ของแต่ละคำขอแปลประกอบด้วยสี่ชั้นเนื้อหาต่อไปนี้:

1. **System Prompt** (`system_prompt_translate_engine.txt`): กำหนดกฎพื้นฐานของงานแปล รวมถึง:
   - ใช้รูปแบบอินพุต-เอาต์พุตคั่นด้วยแท็บ (เพื่อให้โปรแกรมแยกวิเคราะห์ง่าย)
   - เก็บตัวยึดตำแหน่งในข้อความต้นฉบับอย่างเคร่งครัด (`%1`, `{}`, `<>` ฯลฯ) ซึ่งเป็นตัวแปรที่เกมแทนที่แบบไดนามิกขณะรัน
   - ลำดับความสำคัญของอำนาจ: คำแปลภาษาปลายทางที่ตรวจสอบโดยมนุษย์ > อภิธานศัพท์ > การอ้างอิง RAG > การตัดสินใจของ LLM เอง
   - คำแปลแต่ละรายการต้องมีคะแนนความเชื่อมั่น (1.0 แน่นอน ~ 0.1 คาดเดา)
   - กำหนดให้ LLM ลดการใช้โทเค็นในกระบวนการอนุมานให้น้อยที่สุด เพื่อลดค่าใช้จ่าย API

2. **โครงร่างการแปล** (`translation_schema_zh-hans.md`): กำหนดข้อกำหนดรูปแบบการแปลภาษาจีน เช่น:
   - เครื่องหมายวรรคตอน: ใช้เครื่องหมายวรรคตอนครึ่งมุมแบบอังกฤษเป็นหลัก ยกเว้นเครื่องหมายเฉพาะของจีน เช่น `、` `...` `《》`
   - การตั้งชื่อไอเท็ม: `ชื่อไอเท็ม (สี, คุณภาพ, คำอธิบาย)`
   - การตั้งชื่อปืน: `ยี่ห้อ+รุ่น+ประเภท`
   - การตั้งชื่อยานพาหนะ: `ปี+ยี่ห้อ+รุ่น+คำอธิบายพิเศษ+ประเภท`

3. **อภิธานศัพท์** (`translation_dictionary_zh-hans.json`): ตารางการแมปศัพท์บังคับ เมื่อมีคำศัพท์ในอภิธานศัพท์ปรากฏในข้อความต้นฉบับ LLM ต้องใช้คำแปลจีนที่กำหนด ไม่สามารถเลือกเองได้

4. **บริบท RAG**: ตัวอย่างคำแปลอ้างอิงที่ค้นคืนโดย `RagContextRetriever` ฝังอยู่ใน Prompt เพื่อใช้เป็นข้อมูลอ้างอิงในการแปล

**รูปแบบอินพุตและเอาต์พุต**:

อินพุต (แต่ละรายการที่ต้องแปล):
```
T1\t<source_text>\t<multi_lang_context>\t<rag_context>\t<mod_info>
```

เอาต์พุต (ผลการแปลแต่ละรายการ):
```
T1\t<translation>\t<confidence>\t[comment]
```

การใช้รูปแบบคั่นด้วยแท็บเพื่อให้ผลลัพธ์ของ LLM สามารถแยกวิเคราะห์ได้อย่างแม่นยำ — การคั่นด้วยจุลภาคหรือช่องว่างอาจสับสนกับเนื้อหาข้อความเอง

**กลไก Warmup**:

เมื่อจำนวนชุดการแปลมากกว่า 5 ชุด ไปป์ไลน์จะส่งคำขอล่วงหน้า (ประกอบด้วยงานแปลจำนวนน้อย) ก่อน จุดประสงค์ของการวอร์มอัพมีสามประการ:

1. **ตรวจสอบการเชื่อมต่อ API**: ยืนยันว่าเครือข่ายเข้าถึงได้และ API Key ยังใช้ได้
2. **ตรวจสอบสถานะบัญชี**: หาก API ส่งคืนข้อผิดพลาด `AccountFatal` (เงินไม่พอหรือบัญชีถูกระงับ) ให้ยุติงานแปลที่เหลือทั้งหมด หลีกเลี่ยงการล้มเหลวซ้ำซ้อนอย่างไร้ความหมาย
3. **เพิ่มอัตราการ hit แคช**: คำขอล่วงหน้าจะส่งส่วนหัว Prompt ที่ใช้ร่วมกับชุดงานจริง (system prompt + กฎ) ทำให้ KV Cache ฝั่งบริการ LLM สามารถนำกลับมาใช้ใหม่ได้โดยตรงในการแปลจริง ลดต้นทุนการอนุมานและความหน่วง

### 3.12 ResultWriter (`ResultWriterService`)

**หน้าที่**: เขียนข้อมูลทั้งหมดที่ไปป์ไลน์สร้างขึ้น (ผลการแปล เวกเตอร์ฝัง ข้อมูลเมตา ฯลฯ) กลับสู่ระบบไฟล์อย่างถาวร เพื่อให้ใช้ซ้ำในการรันครั้งต่อไป

`ResultWriter` คือ "โมดูลจัดเก็บ" ของไปป์ไลน์ ผลการแปลที่เกิดจากการรันแต่ละครั้งต้องถูกบันทึกไว้ มิฉะนั้นการรันครั้งต่อไปจะไม่สามารถระบุได้ว่าข้อความใดแปลแล้ว ส่งผลให้ต้องทำงานซ้ำจำนวนมาก

**เป้าหมายและรูปแบบผลลัพธ์**:

| ประเภทข้อมูล | ตำแหน่งจัดเก็บ | รูปแบบ |
|-------------|---------------|--------|
| ข้อมูลเมตาม็อด | `data/modinfos.json` | อาร์เรย์ JSON บันทึกข้อมูลม็อดที่ประมวลผลทั้งหมด |
| รายการคำแปล | `data/translations/<iso>/<modId>.txt` | รูปแบบบรรทัดคำแปล PZ: `key::lang::status = "value"` |
| เวกเตอร์ฝัง | `data/embeddings/<modId>.bin` | รูปแบบไบนารีบีบอัด Zstd (ประหยัดพื้นที่ดิสก์) |
| ข้อมูลเมตาของรายการ | `data/entry_metadata/<bucket>/<modId>.json` | รูปแบบ JSON บันทึกสถานะ เช่น sourceHash, isActive |

**คำอธิบายรูปแบบบรรทัดคำแปล**:
```
ContextMenu_PickUp::en = "Pick Up",
ContextMenu_PickUp::zh-hans::unverified = "拾起",
```

- บรรทัดแรกคือ **บรรทัดภาษาต้นฉบับ** (`::en`) บันทึกข้อความต้นฉบับภาษาอังกฤษ
- บรรทัดที่สองคือ **บรรทัดภาษาปลายทาง** (`::zh-hans::unverified`) บันทึกผลการแปล `unverified` แสดงว่าแปลโดย LLM อัตโนมัติ ยังไม่ผ่านการตรวจสอบโดยมนุษย์ หากภายหลังมีการตรวจสอบยืนยันด้วยมนุษย์ สถานะสามารถอัปเดตเป็น `verified` ได้

**เจตนาการออกแบบ — รูปแบบแคชภายใน**: การเลือกใช้ `key::lang::status = "value"` แทน JSON เป็นรูปแบบแคชภายใน เนื่องจากรูปแบบนี้มีความหนาแน่นของข้อมูลสูงกว่า และเมื่อตรวจสอบเนื้อหาคำแปลด้วยมนุษย์ สามารถแสดงข้อมูลบริบทเพิ่มเติมบนหน้าจอได้มากขึ้น

### 3.13 FinalOutputWriter (`FinalOutputWriterService`)

**หน้าที่**: แปลงแคชคำแปลที่ไปป์ไลน์สะสมไว้เป็นไฟล์รูปแบบม็อด PZ ที่ผู้เล่นสามารถนำไปใช้ได้โดยตรง

`ResultWriter` จัดเก็บคำแปลในรูปแบบภายในของไปป์ไลน์ (เพื่อให้สะดวกต่อการประมวลผลแบบเพิ่มหน่วยและการติดตามสถานะ) แต่รูปแบบนี้ไม่สามารถโหลดโดยเกม Project Zomboid ได้โดยตรง `FinalOutputWriter` รับผิดชอบแปลงรูปแบบภายในเป็นไฟล์เผยแพร่สุดท้ายที่สอดคล้องกับข้อกำหนดม็อด PZ

**โครงสร้างไดเรกทอรีผลลัพธ์**:

```
final_outputs/project_babel/contents/mods/project_babel/
├── 42/media/lua/shared/Translate/<gameCode>/*.json
└── 42.19/media/lua/shared/Translate/<gameCode>/*.json
```

- `42` และ `42.19` สอดคล้องกับเกมเวอร์ชันหลักสองเวอร์ชันของ PZ (Build 42 และ Build 42.19) เวอร์ชันต่างกันโหลดไฟล์คำแปลจากไดเรกทอรีต่างกัน
- เนื้อหาของทั้งสองไดเรกทอรีเหมือนกัน — ไปป์ไลน์เขียนเวอร์ชัน 42.19 ก่อน จากนั้นคัดลอกไปยังไดเรกทอรี 42

**ตรรกะการประมวลผลหลัก**:

1. **แยกข้อความต้นฉบับของเกม**: โหลดไฟล์ JSON ทั้งหมดในไดเรกทอรี `base_game_keys/` สร้างชุดคีย์แปล (translationKey) ที่เกมต้นฉบับมีอยู่แล้ว คีย์เหล่านี้มีคำแปลอย่างเป็นทางการในเกมต้นฉบับ ไปป์ไลน์ไม่ต้องแปลซ้ำ รายการที่ตรงกับคีย์เหล่านี้จะไม่ถูกเขียนในผลลัพธ์สุดท้าย

2. **แยกรายการม็อดอ้างอิง**: รายการของม็อดคำแปลอ้างอิงเป็นคำแปลที่มนุษย์ทำ ไปป์ไลน์จะไม่เขียนรายการเหล่านี้ในไฟล์เผยแพร่สุดท้าย (เพื่อหลีกเลี่ยงข้อพิพาทด้านลิขสิทธิ์)

3. **เส้นทางตามคำนำหน้าไปยังไฟล์**: คำนำหน้าของคีย์แปล (translationKey) กำหนดว่าจะเขียนลงในไฟล์ผลลัพธ์ใด ตัวอย่าง:
   - คีย์ขึ้นต้นด้วย `IG_UI_` → เขียนใน `IG_UI.json`
   - คีย์ขึ้นต้นด้วย `ContextMenu_` → เขียนใน `ContextMenu.json`
   - คีย์ขึ้นต้นด้วย `Tooltip_` → เขียนใน `Tooltip.json`

   การแมปนี้มาจาก `translation_key_to_file_mapping` ที่บันทึกในขั้นตอน `ContentExtractor`

4. **การเขียนแบบอะตอม**: ไฟล์ผลลัพธ์ทั้งหมดใช้กลยุทธ์ "เขียนไฟล์ชั่วคราวก่อน แล้วย้ายแบบอะตอม" — เขียน `<filename>.tmp` ก่อน เมื่อเขียนสำเร็จจึงใช้ `File.Move` เพื่อเขียนทับไฟล์เป้าหมาย วิธีนี้ช่วยให้มั่นใจได้ว่าแม้จะเกิดการขัดข้องหรือไฟฟ้าดับระหว่างการเขียน ไฟล์ที่มีอยู่เดิมจะไม่เสียหาย

### 3.14 ProgressReporter (`ProgressReporterService`)

**หน้าที่**: คำนวณอัตราความครอบคลุมการแปลของแต่ละภาษาและสร้างรายงานความคืบหน้าหลายภาษา เพื่อให้ชุมชนทราบความคืบหน้าของการแปล

รายงานความคืบหน้าอยู่ในรูปแบบ Markdown จัดเก็บในไดเรกทอรี `docs/progress/` แต่ละภาษาจะมีไฟล์รายงานของตนเอง (เช่น `progress_zh-hans.md`, `progress_ja.md`)

**ขั้นตอนการสร้าง**:

1. **โหลดเทมเพลต**: อ่าน `src/prompt_templates/progress/progress_template_<lang>.md` แต่ละภาษาสามารถใช้เทมเพลตของตนเองได้ เทมเพลตประกอบด้วยตัวแปรตัวยึดตำแหน่งรูปแบบ `{{PLACEHOLDER}}`
2. **การคำนวณสถิติ**: วนซ้ำแคชรายการคำแปลทั้งหมด คำนวณตัวชี้วัดต่อไปนี้สำหรับแต่ละภาษาปลายทาง:
   - `total`: จำนวนรายการที่ต้องแปลทั้งหมดของภาษานั้น
   - `translated`: จำนวนรายการที่แปลเสร็จแล้ว
   - `pending`: จำนวนรายการที่ยังไม่ได้แปล
   - `untranslatable`: จำนวนรายการที่ถูกทำเครื่องหมายว่าไม่สามารถแปลได้ (เนื่องจากถูกกรองโดยการตรวจสอบเนื้อหา)
3. **แทนที่ตัวยึดตำแหน่ง**: แทนที่ `{{PLACEHOLDER}}` ในเทมเพลตด้วยข้อมูลสถิติจริง
4. **เขียนไฟล์**: เขียนเนื้อหาที่แทนที่แล้วลงใน `docs/progress/progress_<iso>.md`

## 4. ข้อตกลงข้อมูล

ส่วนนี้อธิบายรายละเอียดโครงสร้างข้อมูลหลัก รูปแบบไฟล์ และข้อตกลงคีย์ดัชนีที่ใช้ในไปป์ไลน์ คำจำกัดความเหล่านี้เป็นพื้นฐานสำหรับการทำความเข้าใจวิธีการส่งผ่านข้อมูลระหว่างโมดูลต่าง ๆ

### 4.1 ประเภทหลัก

#### `TranslationEntry` — รายการคำแปล

`TranslationEntry` เป็นโครงสร้างข้อมูลหลักที่สุดในไปป์ไลน์ แทน **ข้อความหนึ่งรายการที่ต้องแปล** แต่ละ TranslationEntry สอดคล้องกับคีย์แปล (translationKey) หนึ่งคีย์ในม็อด ประกอบด้วยข้อมูลครบถ้วน เช่น ข้อความต้นฉบับ คำแปล เวกเตอร์ฝัง เป็นต้น

```csharp
class TranslationEntry {
    string modId;                                          // Steam Workshop Mod ID
    string masterKey;                                      // PZ Lua คีย์หลัก (เช่น "IG_UI")
    string translationKey;                                 // คีย์แปลแบบสมบูรณ์
    Dictionary<string, TranslationData> translationValues; // ISO → ข้อมูลคำแปล
    string baseLang;                                       // ภาษาต้นฉบับ (ค่าเริ่มต้น "en")
    string embeddingHash;                                  // แฮชของข้อความที่ฝังปัจจุบัน
    float[] embeddingVector;                               // [เก่า] เวกเตอร์เดียว (เลิกใช้แล้ว เปลี่ยนเป็น embeddingValues รองรับฝังหลายภาษา)
    Dictionary<string, TranslationEmbedding> embeddingValues; // embeddingKey → เวกเตอร์+แฮช (แทนที่ embeddingVector)
    bool isActive;                                         // ยังมีอยู่ในไฟล์ต้นฉบับหรือไม่
    DateTime lastSeenAt;
    DateTime lastSeenModUpdated;
    string sourceHash;                                     // SHA256 ของข้อความต้นฉบับ
    List<ContainingFileInfo> containingFileInfos;          // ข้อมูลไฟล์ต้นฉบับทั้งหมด
}
```

**ตัวระบุที่ไม่ซ้ำทั่วโลก**: แต่ละ `TranslationEntry` ถูกระบุโดย `modId::translationKey` ตัวอย่างเช่น `1234567890::IG_UI_NewGame` แทนข้อความ `IG_UI_NewGame` ในม็อด `1234567890`

**เมธอดสำคัญ**:

- `GetBaseTextStrict()`: ใช้ `baseLang` (โดยปกติคือ `en`) อย่างเคร่งครัดเพื่อรับข้อความต้นฉบับ นี่คือแหล่งอินพุตสำหรับการแปล
- `GetSourceText()`: วิธีการรับข้อความที่มีกลไก fallback โดยเรียงลำดับ: ภาษาที่ร้องขอ → ภาษาต้นฉบับ → คำแปลที่ตรวจสอบแล้วใด ๆ → คำแปลที่มีข้อความใด ๆ วิธีนี้ให้ความทนทานต่อข้อผิดพลาดเมื่อข้อความต้นฉบับขาดหาย

#### `TranslationData` — ข้อมูลคำแปล

`TranslationData` จัดเก็บคำแปลของหนึ่งรายการและข้อมูลเมตา

```csharp
class TranslationData {
    string text;           // คำแปล
    bool isVerified;       // ตรวจสอบแล้วหรือไม่ (คำแปลอ้างอิงเป็น true)
    float? confidence;     // ระดับความเชื่อมั่นของคำแปล LLM (0.0~1.0)
    string status;         // สถานะการตรวจสอบ: "verified" หรือ "unverified"
    string processStatus;  // สถานะการประมวลผล: "processed" หรือ "unprocessed"
    List<string> comments; // รายการความคิดเห็น
}
```

- `isVerified = true`: คำแปลนี้มาจากม็อดอ้างอิงที่แปลโดยมนุษย์ มีคุณภาพน่าเชื่อถือ
- `isVerified = false`: คำแปลนี้มาจาก LLM ทำเครื่องหมายเป็น `unverified` ยังไม่ผ่านการตรวจสอบโดยมนุษย์
- `confidence`: คะแนนความเชื่อมั่นที่ LLM ส่งคืนเมื่อสร้างคำแปลนี้ `null` หมายถึงไม่ใช่คำแปลจาก LLM
- `processStatus`: ถูกประมวลผลโดยไปป์ไลน์ LLM แล้วหรือไม่ (`processed` หรือ `unprocessed`)

#### `ModInfo` — ข้อมูลเมตาม็อด

`ModInfo` จัดเก็บข้อมูลเมตาครบถ้วนของม็อด Steam Workshop หนึ่งรายการ ติดตามสถานะและการอัปเดต

```csharp
struct ModInfo {
    string modId;
    string modName;
    string creator;
    string? language;
    string localDownloadedPath;
    DateTime timeModUpdated;       // เวลาอัปเดตล่าสุดที่ Steam บันทึก
    DateTime timeModCreated;       // เวลาเผยแพร่ครั้งแรกที่ Steam บันทึก
    DateTime timeLastChecked;      // เวลาที่ไปป์ไลน์ตรวจสอบม็อดนี้ครั้งล่าสุด
    int subscription;              // จำนวนการสมัครรับ (จาก Steam)
    int favorite;                  // จำนวนการถูกใจ (จาก Steam)
    string description;            // ข้อความคำอธิบายม็อดจาก Steam
    int consumerAppId;             // Steam consumer App ID (108600 = PZ)
    ContentCheckStatus contentCheckStatus; // สถานะการตรวจสอบเนื้อหา
    bool needsUpdate;              // ต้องแยกและแปลใหม่หรือไม่
    bool needsContentCheck;        // ต้องตรวจสอบเนื้อหาใหม่หรือไม่
    bool isAvailable;              // ม็อดเข้าถึงได้หรือไม่ (false = ไม่ใช่ PZ mod หรือถูกลบ)
    DateTime timeNextContentCheck; // เวลาที่กำหนดให้ตรวจสอบเนื้อหาครั้งถัดไป
    string lastFetchStatus;        // สถานะการสอบถาม Steam ครั้งล่าสุด
    double contentCheckConfidence; // ระดับความเชื่อมั่นการตรวจสอบเนื้อหา (0.0~1.0)
    bool contentCheckNeedHumanReview; // ต้องตรวจสอบด้วยมนุษย์หรือไม่
    string contentCheckRiskLevel;  // ระดับความเสี่ยง (safe/low/medium/high)
    string contentCheckReason;     // เหตุผลสรุปผลการตรวจสอบ
    string contentCheckViolatedRulesJson; // รายการกฎที่ละเมิด (JSON)
}
```

**ฟิลด์สถานะสำคัญ**:

- `needsUpdate`: ตั้งเป็น `true` เมื่อ `time_updated` ที่ Steam บันทึกช้ากว่า `timeModUpdated` ในแคช แสดงว่าผู้สร้างม็อดอัปเดตเนื้อหา
- `isAvailable`: หาก `consumer_app_id` ที่ Steam API ส่งคืนไม่ใช่ `108600` (Project Zomboid) หรือม็อดถูกลบ จะตั้งเป็น `false` โมดูลต่อมาจะข้ามม็อดนี้
- `contentCheckStatus`: สถานะการตรวจสอบความปลอดภัยของเนื้อหา ดูคำอธิบายสเตตแมชชีนในหัวข้อ 4.4

#### `TranslationBatch` — ชุดการแปล

`TranslationBatch` คือหน่วยพื้นฐานสำหรับการแปลด้วย LLM ประกอบด้วยรายการที่ต้องแปลของม็อดเดียวกันและภาษาปลายทางเดียวกัน

```csharp
class TranslationBatch {
    int batchId;
    int priority;                    // ลำดับความสำคัญ (คำนวณจาก subscription + favorite)
    string modId;
    List<TranslationEntry> translationEntries;
    string baseLang;                 // "en"
    string targetLang;               // รหัส ISO ภาษาปลายทาง เช่น "zh-hans"
}
```

- `priority`: คำนวณจากจำนวนการสมัครรับและการถูกใจของม็อด ม็อดยอดนิยมได้รับการแปลก่อน
- รายการทั้งหมดในชุดเดียวกันมาจากม็อดเดียวกัน เพื่อหลีกเลี่ยงความสับสนของบริบทข้ามม็อด

#### `LangInfoData` — ข้อมูลภาษา

`LangInfoData` กำหนดภาษาที่รองรับหนึ่งภาษา ประกอบด้วยการแมปรหัสในเกมและรหัส ISO มาตรฐาน

```csharp
class LangInfoData {
    string ingameCode;    // รหัสในเกม (CN, EN, JP...)
    string chineseName;   // ชื่อภาษาจีน
    string englishName;   // ชื่อภาษาอังกฤษ
    string nativeName;    // ชื่อภาษาท้องถิ่น (日本語, 한국어...)
    string isoCode;       // รหัสภาษา ISO 639-1 หรือ BCP 47 (zh-hans, en, ja...)
}
```

### 4.2 รูปแบบไฟล์

ไปป์ไลน์ใช้รูปแบบไฟล์ที่แตกต่างกันในขั้นตอนการประมวลผลต่าง ๆ ต่อไปนี้จะอธิบายตามลำดับการไหลของข้อมูลในไปป์ไลน์

#### ผลลัพธ์การแยก (ผลผลิตของ ContentExtractor)

หลังจาก `ContentExtractor` แยกข้อความจากไฟล์ม็อด จะส่งออกในรูปแบบต่อไปนี้ไปยัง `extracted_contents/<iso>/<modId>.txt`:

```
<translationKey>::en = "original text",
<translationKey>::<iso>::unverified = "translated text",
```

บรรทัดแรกคือบรรทัดภาษาต้นฉบับ (ข้อความต้นฉบับภาษาอังกฤษ) บรรทัดที่สองคือบรรทัดภาษาปลายทาง หากม็อดขาดข้อความต้นฉบับภาษาอังกฤษ (กรณีที่รุนแรง) จะข้ามบรรทัดต้นฉบับแต่ยังเขียนบรรทัดปลายทาง

#### ไฟล์การแมปคีย์

`extracted_contents/translation_key_to_file_mapping/<modId>.json`:

```json
{
  "IG_UI_SomeKey": "IG_UI.json",
  "ContextMenu_PickUp": "ContextMenu.json"
}
```

การแมปนี้บันทึกว่า `translationKey` แต่ละคีย์มาจากไฟล์ต้นฉบับใด ในขั้นตอนการส่งออกสุดท้าย `FinalOutputWriter` จะใช้การแมปนี้เพื่อส่งคีย์แปลไปยังไฟล์ JSON เอาต์พุตที่ถูกต้อง

#### แคชคำแปล (data/translations/)

แคชคำแปลแบบถาวร จัดเก็บใน `data/translations/<iso>/<modId>.txt` รูปแบบเดียวกับผลลัพธ์การแยก:

```
<translationKey>::en = "source text",
<translationKey>::<iso>::unverified = "translation",
```

แคชคือหัวใจของ "หน่วยความจำ" ของไปป์ไลน์ — ทุกครั้งที่รัน `RepoDataLoader` จะกู้คืนผลการแปลที่มีอยู่เดิมจากที่นี่

#### ผลลัพธ์สุดท้าย (final_outputs/)

ไฟล์คำแปลที่ผู้เล่นสามารถใช้ได้โดยตรง ส่งออกในรูปแบบ JSON:

```json
{
  "IG_UI_SomeKey": "ข้อความแปล",
  "ContextMenu_SomeKey": "ข้อความแปล"
}
```

ใช้การเข้ารหัส UTF-8 without BOM, ระยะเยื้อง 2 ช่องว่าง สอดคล้องกับข้อกำหนดไฟล์คำแปลของ Project Zomboid

#### เวกเตอร์ฝัง (data/embeddings/*.bin)

ใช้รูปแบบไบนารีบีบอัด Zstd โดย `BinaryEmbeddingSerializer` ทำการซีเรียลไลซ์ โครงสร้างไฟล์:

- **Header**: จำนวนรายการ (int32)
- **แต่ละระเบียน**: ความยาว key (varint) + สตริง key (UTF-8) + แฮช SHA256 (32 bytes) + ข้อมูลเวกเตอร์ (384 × float32)

การบีบอัด Zstd ในกรณีของเวกเตอร์ 384 มิติให้อัตราส่วนการบีบอัดประมาณ 4:1 ลดการใช้พื้นที่ดิสก์อย่างมีนัยสำคัญ

### 4.3 ข้อตกลงคีย์ดัชนี

| สถานการณ์ | รูปแบบ | ตัวอย่าง |
|-----------|--------|----------|
| คีย์ที่ไม่ซ้ำทั่วโลกของ TranslationEntry | `modId::translationKey` | `1234567890::IG_UI_NewGame` |
| EmbeddingKey | `base:targetLang` | `en:zh-hans` |
| คีย์บริบท RAG | `modId::translationKey` | เหมือน TranslationEntry |

### 4.4 สเตตแมชชีน

ในไปป์ไลน์มีตรรกะการเปลี่ยนสถานะที่สำคัญสามชุด ซึ่งควบคุมการตรวจสอบเนื้อหา คุณภาพการแปล และการอัปเดตม็อด

#### สถานะการตรวจสอบเนื้อหา ContentCheck

การเปลี่ยนสถานะการตรวจสอบเนื้อหาอย่างสมบูรณ์:

```
UNKNOWN ──(ตรวจสอบม็อดใหม่ครั้งแรก)──→ NEEDVERIFICATION
                                  ├──(LLM ตรวจสอบ: ปลอดภัย)──→ ACCEPTED
                                  ├──(LLM ตรวจสอบ: ละเมิด)──→ REJECTED
                                  └──(LLM ตรวจสอบ: ไม่แน่ใจ, ความเชื่อมั่น<0.7)──→ NEEDVERIFICATION (รอการตรวจสอบด้วยมนุษย์)

ACCEPTED ──(เกินระยะเวลาแคช 90 วัน)──→ NEEDVERIFICATION (ตรวจสอบซ้ำเป็นระยะ)
```

- **UNKNOWN**: ม็อดที่พบใหม่ ยังไม่เคยตรวจสอบเนื้อหา
- **NEEDVERIFICATION**: ต้องตรวจสอบ (หรือตรวจสอบซ้ำ) ไปป์ไลน์จะเรียก LLM เพื่อสแกนความปลอดภัยของเนื้อหาม็อดนี้
- **ACCEPTED**: ผ่านการตรวจสอบ เนื้อหาม็อดปลอดภัย สามารถแปลได้ตามปกติ
- **REJECTED**: ไม่ผ่านการตรวจสอบ ม็อดนี้มีเนื้อหาละเมิด ข้ามการแปล

#### สถานะการตรวจสอบคำแปล TranslationData

ความน่าเชื่อถือของข้อมูลคำแปลแต่ละรายการแยกตามเครื่องหมาย `isVerified`:

| สถานะ | `isVerified` | ความหมาย |
|-------|-------------|----------|
| ตรวจสอบแล้ว (แปลโดยมนุษย์) | `true` | มาจากม็อดคำแปลอ้างอิง แปลและยืนยันโดยมนุษย์ |
| ยังไม่ตรวจสอบ (แปลโดย AI) | `false` | แปลโดย LLM อัตโนมัติ ทำเครื่องหมาย `unverified` ยังไม่ผ่านการตรวจสอบด้วยมนุษย์ |
| รอการแปล | ไม่มีข้อความ | ยังไม่ได้แปล `translationValues` ไม่มีคำแปลสำหรับภาษานี้ |

#### การตัดสิน `ModInfo.needsUpdate` ว่าต้องอัปเดตหรือไม่

การที่ม็อดต้องแยกและแปลใหม่ กำหนดโดยกฎต่อไปนี้:

- `time_updated` ของ Steam ช้ากว่า `timeModUpdated` ในแคช → `needsUpdate = true` (ผู้สร้างม็อดเผยแพร่อัปเดต)
- ม็อดที่เข้าถึงได้และไม่มีรายการคำแปลในแคช → `needsUpdate = true` (ประมวลผลม็อดนี้ครั้งแรก)
- ม็อดที่แยกแล้วมี 0 รายการคำแปล → ตั้งสถานะการตรวจสอบเนื้อหาเป็น `ACCEPTED` โดยตรง (ม็อดนี้ไม่มีข้อความที่ต้องแปล ไม่จำเป็นต้องแปล)

## 5. คำอธิบายการกำหนดค่า

ในไดเรกทอรี `config/` มีไฟล์กำหนดค่าทั้งหมด 5 ไฟล์ แบ่งตามหน้าที่เป็น การควบคุมไปป์ไลน์ การจัดการคีย์ลับ คำจำกัดความภาษา คลังข้อความอ้างอิง และคำขอแปล

### 5.1 `config/config.json` — การกำหนดค่าหลักของไปป์ไลน์

ไฟล์ควบคุมหลักของไปป์ไลน์แปลทั้งหมด ฟิลด์ทั้งหมดเป็นฟิลด์บังคับ เว้นแต่จะระบุ "ตัวเลือก"

#### 5.1.1 `LLM` — การกำหนดค่าโมเดลภาษาขนาดใหญ่

| ฟิลด์ | ประเภท | ค่าเริ่มต้น | คำอธิบาย |
|-------|--------|------------|----------|
| `api_endpoint` | string | `https://api.deepseek.com/chat/completions` | ที่อยู่ API LLM รองรับโปรโตคอล OpenAI Chat Completions |
| `model` | string | `deepseek-v4-flash` | ชื่อโมเดล หากมี `v4-flash` หรือ `v4-pro` จะเรียกใช้โปรไฟล์การทำงานพร้อมกันอัตโนมัติที่สอดคล้องกัน |
| `temperature` | float | `0.1` | อุณหภูมิการสุ่มตัวอย่าง (0~2) ยิ่งต่ำยิ่งเอาต์พุตแน่นอน งานแปลแนะนำ ≤0.3 |
| `max_tokens` | int | `380000` | จำนวนโทเค็นสูงสุดของการตอบสนอง API ต่อครั้ง ต้องมากกว่าปริมาณเอาต์พุตรวมของชุด |
| `batch_size` | int | `30` | ขีดจำกัดจำนวนรายการต่อชุดการแปล อยู่ภายใต้ข้อจำกัดร่วมกับ `batch_token_budget` |
| `batch_token_budget` | int | `2000` | ขีดจำกัดงบประมาณโทเค็นฝั่งอินพุตต่อชุด (ประมาณคร่าว ๆ) `0` หมายถึงไม่จำกัด |
| `request_timeout_seconds` | int | `300` | เวลาหมดเวลาคำขอ HTTP ต่อครั้ง ชุดใหญ่ต้องเพิ่มให้เหมาะสม |

**`concurrency` — การควบคุมการทำงานพร้อมกัน** (ออบเจ็กต์ย่อย):

| ฟิลด์ | ประเภท | ค่าเริ่มต้น | คำอธิบาย |
|-------|--------|------------|----------|
| `initial` | int | `0` | จำนวนการทำงานพร้อมกันเริ่มต้น `0` = ตรวจจับอัตโนมัติตามสภาพแวดล้อมและโมเดล |
| `maximum` | int | `0` | ขีดจำกัดการทำงานพร้อมกันสูงสุด `0` = ตรวจจับอัตโนมัติ ในโหมดไดนามิก เมื่อ success streak ถึงเกณฑ์จะค่อยๆ เพิ่มขึ้นถึงค่านี้ |
| `minimum` | int | `1` | ขีดจำกัดการทำงานพร้อมกันขั้นต่ำ ในโหมดไดนามิกเมื่อลดขนาดจะไม่ต่ำกว่าค่านี้ |
| `max_retries` | int | `5` | จำนวนครั้งสูงสุดที่ลองใหม่สำหรับ work item เดียว |
| `failure_streak_to_decrease` | int | `3` | หลังจากล้มเหลวติดต่อกัน N ครั้งจะลดขนาด (ลดการทำงานพร้อมกันครึ่งหนึ่ง) |
| `retry_base_delay_ms` | int | `1000` | หน่วงเวลาพื้นฐาน (ms) การหน่วงเวลาจริง = base × 2^attempt (backoff แบบเอกซ์โพเนนเชียล) |
| `retry_max_delay_ms` | int | `60000` | ขีดจำกัดหน่วงเวลาสูงสุด (ms) |
| `fixed_concurrency` | int | `128` | **เมื่อ >0 จะเปิดใช้โหมดหน้าต่างคงที่**: การทำงานพร้อมกันภายในหน้าต่าง, เรียงลำดับระหว่างหน้าต่าง ไม่ใช้การปรับแบบไดนามิก ตั้งเป็น 0 ใช้โหมดไดนามิก |

**คำอธิบายโหมดการทำงานพร้อมกัน**:

- **โหมดไดนามิก** (`fixed_concurrency=0`): ปรับการทำงานพร้อมกันอัตโนมัติตามความสำเร็จ/ล้มเหลว เหมาะสำหรับสถานการณ์ที่กลยุทธ์การจำกัดอัตราของ API ไม่โปร่งใส
- **โหมดหน้าต่างคงที่** (`fixed_concurrency>0`): พฤติกรรมการทำงานพร้อมกันที่กำหนดได้ เหมาะสำหรับสถานการณ์ที่ทราบขีดจำกัดการทำงานพร้อมกันของ API มีบันทึกการเสร็จสิ้นระหว่างหน้าต่าง

**โปรไฟล์อัตโนมัติ** (เมื่อ `initial=0` หรือ `maximum=0`): ไปป์ไลน์จะเลือกพารามิเตอร์การทำงานพร้อมกันที่เหมาะสมตามสภาพแวดล้อมและชื่อโมเดล ดูรายละเอียดใน [หัวข้อ 3.11 — การตรวจจับโปรไฟล์การทำงานพร้อมกันอัตโนมัติ](#311-llmtranslator-llmtranslatorservice)

### 5.2 `config/secrets.json` — การกำหนดค่าคีย์ลับ

> **⚠️ ไฟล์นี้มีข้อมูลที่ละเอียดอ่อน ถูกเพิ่มใน `.gitignore` ห้ามส่งไปยังระบบควบคุมเวอร์ชันโดยเด็ดขาด**

ก่อนใช้งานให้คัดลอก `secrets_example.json` เป็น `secrets.json` และกรอกค่าจริง

| ฟิลด์ | ประเภท | คำอธิบาย |
|-------|--------|----------|
| `LLM_KEY` | string | คีย์ตรวจสอบสิทธิ์ของ LLM API `ConfigReader` จะตรวจสอบว่าไม่ว่างเปล่า หากว่างเปล่าไปป์ไลน์จะหยุดทำงาน |
| `STEAM_KEY` | string | Steam Web API Key ใช้เรียกอินเทอร์เฟซเช่น `ISteamRemoteStorage/GetPublishedFileDetails` รับได้ที่: [Steam พอร์ทัลนักพัฒนา](https://steamcommunity.com/dev/apikey) |
| `EMBEDDING_HOST` | string | ที่อยู่โฮสต์ของบริการฝัง (IP หรือโดเมน ไม่รวมพอร์ต) พอร์ตระบุโดย `EMBEDDING_PORT` แยกต่างหาก |
| `EMBEDDING_PORT` | string | หมายเลขพอร์ตของบริการฝัง |
| `EMBEDDING_KEY` | string | คีย์ที่แชร์ล่วงหน้าสำหรับการเข้ารหัส AES-256 ของบริการฝัง หลังจากแฮช SHA256 แล้วใช้เป็นคีย์ AES-GCM |

**ตรรกะการตรวจสอบคีย์ลับ**: `ConfigReader.LoadConfig()` หลังจากโหลดเสร็จจะตรวจสอบว่า `LLM_KEY` ว่างเปล่าหรือไม่ → หากว่างเปล่าให้ข้อยกเว้น → `Program.cs` จับแล้ว `Environment.Exit(1)`

### 5.3 `config/supported_languages.json` — รายการภาษาที่รองรับ

กำหนดภาษาปลายทางทั้งหมดที่ไปป์ไลน์รองรับ แต่ละระเบียนสอดคล้องกับประเภท `LangInfoData`

ก่อนใช้งานให้คัดลอก `supported_languages_example.json` เป็น `supported_languages.json`

| ฟิลด์ | ประเภท | คำอธิบาย |
|-------|--------|----------|
| `ingame_code` | string | รหัสภาษาในเกม PZ สอดคล้องกับชื่อโฟลเดอร์ใน `Translate/` เช่น `CN`, `JP`, `DE` |
| `chinese_name` | string | ชื่อภาษาจีน ใช้ในรายงานความคืบหน้าและบันทึก |
| `english_name` | string | ชื่อภาษาอังกฤษ ใช้ในรายงานความคืบหน้า |
| `native_name` | string | ชื่อภาษาท้องถิ่น ใช้ในรายงานความคืบหน้า |
| `iso_code` | string | รหัสภาษา ISO 639-1 หรือ BCP 47 ใช้ในพาธไฟล์ พารามิเตอร์ API และดัชนีภายใน เช่น `zh-hans`, `ja`, `de` |

**ตัวอย่างรายการ**:
```json
{
  "ingame_code": "CN",
  "chinese_name": "简体中文",
  "english_name": "Chinese (Simplified)",
  "native_name": "简体中文",
  "iso_code": "zh-hans"
}
```

**รายการภาษาที่กำหนดไว้ล่วงหน้า** (27 ภาษา):
`AR` `CA` `CH` `CN` `CS` `DA` `DE` `EN` `ES` `FI` `FR` `HU` `ID` `IT` `JP` `KO` `NL` `NO` `PH` `PL` `PT` `PTBR` `RO` `RU` `TH` `TR` `UA`

**การใช้งานในไปป์ไลน์**:
- **ภาษาต้นฉบับ** (`baseLang`): ใช้ `EN` ในรายการเป็นหลัก `baseIso` ใน `ContentExtractor` แมปจาก `config.baseLanguage`
- **ภาษาปลายทาง** (`targetLangs`): ทุกภาษาที่ไม่ใช่ `EN` ในรายการเป็นเป้าหมายการแปล
- **ภาษาที่ส่งออก** (`outputLangs`): ทุกภาษา (รวม `EN`) มีส่วนร่วมในการส่งออกสุดท้าย

### 5.4 `config/ref_translation_mods.json` — ม็อดคำแปลอ้างอิง

กำหนดม็อดภาษาแปลคุณภาพสูงที่มีอยู่แล้ว ใช้เป็นคลังข้อความอ้างอิงสำหรับการค้นคืนแบบ RAG

| ฟิลด์ | ประเภท | คำอธิบาย |
|-------|--------|----------|
| `mod_id` | string | Steam Workshop Mod ID (ตัวเลข 19 หลัก) |
| `mod_name` | string | ชื่อม็อดอ้างอิง (ใช้สำหรับบันทึกและรายงานเท่านั้น) |
| `language` | string | รหัส ISO ภาษาปลายทางของม็อดอ้างอิงนี้ เช่น `zh-hans` |
| `mod_update_time` | string | เวลาอัปเดตล่าสุดของม็อดที่ Steam บันทึก (สตริง Unix timestamp) |
| `last_check_time` | string | เวลาที่ไปป์ไลน์ตรวจสอบการอัปเดตของม็อดนี้ครั้งล่าสุด (ISO 8601) |

**สิทธิพิเศษของม็อดอ้างอิง**:
- **แคชแยกต่างหาก**: ข้อมูลจัดเก็บใน `translation_ref/` แทน `data/` แยกจากการแปลหลัก
- **ซิงโครไนซ์ก่อน**: ในระยะที่ 2 ดำเนินการดาวน์โหลด/แยก/ฝังก่อนการวนลูปม็อดหลัก
- **อัปเดตแบบเพิ่มหน่วย**: แยกใหม่เฉพาะม็อดที่ `mod_update_time > last_check_time`
- **isVerified=true**: `TranslationData.isVerified` ของรายการคำแปลอ้างอิงทั้งหมดถูกบังคับเป็น `true`
- **ไม่นำเข้าแถวคิวแปล LLM**: รายการของม็อดอ้างอิงจะไม่เข้าสู่แถวคิวการแปล LLM (มีคำแปลโดยมนุษย์แล้ว)
- **ไม่รวมในการส่งออก**: `FinalOutputWriter` กรองรายการม็อดอ้างอิง ไม่เขียนในไฟล์เผยแพร่สุดท้าย

### 5.5 `config/request_for_translation.txt` — คำขอแปลในเครื่อง

รายการรหัสม็อดที่ต้องแปลซึ่งระบุด้วยตนเอง

| กฎ | คำอธิบาย |
|----|----------|
| รูปแบบ | แต่ละบรรทัดมี Steam Workshop Mod ID (ตัวเลขล้วน ๆ) หนึ่งรายการ |
| ความคิดเห็น | บรรทัดที่ขึ้นต้นด้วย `#` ถือเป็นความคิดเห็น จะถูกละเว้น |
| บรรทัดว่าง | ข้ามโดยอัตโนมัติ |
| การตัดซ้ำ | เมื่อรวมกับรายการระยะไกล AsOne ID ที่มีอยู่แล้วจะไม่ถูกเพิ่มซ้ำ |
| การเข้ารหัส | UTF-8 without BOM |

**ตัวอย่าง**:
```
# ม็อดยอดนิยม
2969343830
3000924731

# ม็อดอาวุธ
3502286969
3596827035
```

**ตรรกะการประมวลผล** (`ModIdCollector`):
1. อ่านทุกบรรทัดในไฟล์
2. กรองความคิดเห็น `#` และบรรทัดว่าง
3. ตัดซ้ำ
4. รวมกับรายการระยะไกล AsOne (ระยะไกลเป็นหลัก ไม่เขียนทับที่มีอยู่แล้ว)
5. ID ที่ไม่อยู่ในรายการระยะไกลสร้าง `ModInfo` ค่าเริ่มต้น (สถานะ `UNKNOWN`)

## 7. วิธีการรัน

### การรันในเครื่อง (Windows x64)

```powershell
cd src
dotnet run
```

เมื่อรันในเครื่อง ไปป์ไลน์จะใช้ไฟล์กำหนดค่าในไดเรกทอรี `config/` ก่อนใช้งานครั้งแรก ตรวจสอบให้แน่ใจว่าได้กำหนดค่า `secrets.json` อย่างถูกต้อง (อ้างอิง `secrets_example.json`)

### การรันใน CI (GitHub Actions, Linux x64)

```yaml
- name: Run Translation Pipeline
  run: dotnet run --project src/TranslationPipeline.csproj
```

เมื่อรันในสภาพแวดล้อม GitHub Actions ไปป์ไลน์จะตรวจจับสภาพแวดล้อม CI โดยอัตโนมัติและปรับพฤติกรรม:

- `GITHUB_ACTIONS=true`: ลดขีดจำกัดการทำงานพร้อมกันโดยอัตโนมัติ (เริ่มต้น 4, สูงสุด 32) เพื่อให้เหมาะกับทรัพยากรที่จำกัดของ CI runner
- `RUNNER_OS=Linux`: ปรับให้เข้ากับพาธ Linux และวิธีการจัดการกระบวนการ

### การประเมินผลการรัน

| ผลลัพธ์ | ลักษณะ | ความหมาย |
|---------|--------|----------|
| สำเร็จ | แสดง `Pipeline complete.` รหัสทางออก 0 | ทุกขั้นตอนเสร็จสมบูรณ์ตามปกติ |
| ข้อผิดพลาดร้ายแรง | แสดง `GitHubActions.Error()` รหัสทางออก 1 | ข้อผิดพลาดที่ไม่สามารถกู้คืนได้ เช่น การกำหนดค่าขาดหาย API ไม่พร้อมใช้งาน |
| คำเตือน | แสดง `GitHubActions.Warning()` เขียนไปยัง `temp/run_*/warnings/` | บางขั้นตอนที่ไม่สำคัญล้มเหลว แต่ไปป์ไลน์สามารถดำเนินการต่อได้ |

## 8. การตัดสินใจออกแบบที่สำคัญ

ในกระบวนการออกแบบ Project Babel เราได้ตัดสินใจทางเทคนิคที่สำคัญหลายประการ ตารางต่อไปนี้บันทึกการตัดสินใจแต่ละรายการและเหตุผลเบื้องหลัง เพื่อช่วยให้เข้าใจว่าเหตุใดไปป์ไลน์จึงมีรูปแบบในปัจจุบัน

| การตัดสินใจ | เหตุผลโดยละเอียด |
|------------|------------------|
| **JSON ครอบคลุม TXT** | Project Zomboid เริ่มนำรูปแบบไฟล์คำแปล JSON ใน Build 42 เป็นรูปแบบมาตรฐานใหม่ เมื่อคีย์แปลเดียวกันมีทั้งในไฟล์ TXT และ JSON ไปป์ไลน์จะเลือกใช้ JSON ก่อน — เนื่องจากแสดงถึงรูปแบบเนื้อหาที่ใหม่กว่า และการแยกวิเคราะห์น่าเชื่อถือกว่า หากในอนาคต PZ เลิกใช้รูปแบบ TXT อย่างสมบูรณ์ เพียงแค่ลบตรรกะการแยกวิเคราะห์ TXT ก็พอ |
| **คำแปลอ้างอิงแยกจากการแปลหลัก** | ความถี่ในการเปลี่ยนแปลงของม็อดคำแปลอ้างอิง (แปลโดยมนุษย์) และม็อดทั่วไปที่ต้องแปลนั้นแตกต่างกันอย่างสิ้นเชิง — ครั้งแรกเสถียรและเปลี่ยนแปลงน้อย ครั้งหลังอัปเดตบ่อย หากประมวลผลในวงจรเดียวกัน การอัปเดตเล็กน้อยของคำแปลอ้างอิงจะกระตุ้นการคำนวณใหม่ทั้งหมด สิ้นเปลืองทรัพยากร เมื่อแยกออกมา คำแปลอ้างอิงมีเส้นทางการอัปเดตแบบเพิ่มหน่วยของตนเอง การแปลหลักไม่ได้รับผลกระทบ |
| **การคำนวณฝังใช้บริการระยะไกล** | แม้โมเดล `bge-small-en-v1.5` จะมีขนาดเพียงประมาณ 130MB แต่เมื่อโหลดเข้าหน่วยความจำและรันการอนุมาน การใช้หน่วยความจำจริงมากกว่าขนาดโมเดล ภายใต้ข้อจำกัดหน่วยความจำ 7GB ของ GitHub Actions การรันโมเดลฝังและงานแปลพร้อมกันมีแนวโน้มที่จะเกิด OOM การย้ายการคำนวณฝังไปยังบริการระยะไกลเฉพาะช่วยให้ไปป์ไลน์มีความเสถียร และบริการฝังสามารถใช้ GPU เร่งความเร็วได้ ซึ่งเร็วกว่า CPU อย่างมาก |
| **UDP Knock + การตรวจสอบสิทธิ์ AES** | วิธี API Key แบบเดิมต้องส่งคีย์ในทุกคำขอ HTTP เพิ่มความเสี่ยงในการรั่วไหลของคีย์ รูปแบบ UDP Knock แยกการตรวจสอบสิทธิ์ออกจากการส่งข้อมูล — ตรวจสอบตัวตนผ่าน UDP ก่อน แล้วจึงใช้การเข้ารหัส AES-256-GCM สำหรับการสื่อสาร HTTP แม้ปริมาณ HTTP จะถูกดักจับ หากไม่มีคีย์ที่แชร์ร่วมกันก็ไม่สามารถถอดรหัสได้ ในขณะเดียวกันฝั่งบริการไม่มีสถานะโดยสมบูรณ์ ไม่ต้องบำรุงรักษาเซสชัน |
| **การควบคุมการทำงานพร้อมกันแบบไดนามิก** | กลยุทธ์การจำกัดอัตราของ DeepSeek API ไม่มีค่าที่แน่นอนเปิดเผยสาธารณะ โมเดลต่างกัน ช่วงเวลาต่างกันอาจมีข้อจำกัดต่างกัน ค่าการทำงานพร้อมกันคงที่อาจระมัดระวังเกินไป (เสียปริมาณงาน) หรือรุนแรงเกินไป (ทำให้เกิดข้อผิดพลาด 429 และการลองใหม่จำนวนมาก) การควบคุมการทำงานพร้อมกันแบบปรับตัวได้ด้วยกลยุทธ์ "ทดสอบเมื่อสำเร็จ ลดเมื่อล้มเหลว" จะค้นหาค่าการทำงานพร้อมกันที่เหมาะสมที่สุดในสภาพแวดล้อมปัจจุบันโดยอัตโนมัติ |
| **โหมดหน้าต่างคงที่แบบสำรอง** | ในสภาพแวดล้อมการผลิตที่ทราบขีดจำกัดการทำงานพร้อมกันของ API (เช่น มีข้อตกลง QPS ที่ชัดเจนกับผู้ให้บริการ API) การปรับแบบไดนามิกกลับเพิ่มความไม่แน่นอน โหมดหน้าต่างคงที่ให้พฤติกรรม concurrent ที่กำหนดได้ — แต่ละหน้าต่างมีการทำงานพร้อมกันคงที่ N รายการ เรียงลำดับระหว่างหน้าต่างอย่างเคร่งครัด — ทำให้คาดการณ์ประสิทธิภาพและตรวจสอบปัญหาได้ง่าย |
| **การบีบอัดเวกเตอร์ฝังด้วย Zstd** | ข้อมูลเวกเตอร์ฝัง 384 มิติ × ม็อดหลายหมื่น × รายการหลายหมื่นมีขนาดใหญ่มาก ด้วยรายการนับล้าน ข้อมูลจุดลอยตัวดิบประมาณ 1.5GB การบีบอัด Zstd ให้อัตราส่วนประมาณ 4:1 ลดความต้องการจัดเก็บเหลือประมาณ 375MB และที่สำคัญ Zstd มีความเร็วในการคลายการบีบอัดสูงมาก (>1GB/s) แทบไม่กระทบประสิทธิภาพของไปป์ไลน์ |
| **การเขียนแบบอะตอม ( .tmp + Move)** | หากเกิดการขัดข้องหรือไฟฟ้าดับระหว่างการเขียนไฟล์ อาจทำให้ไฟล์เสียหายครึ่งหนึ่ง เขียนไฟล์ชั่วคราว (`.tmp`) ก่อน เมื่อเขียนสำเร็จจึงใช้ `File.Move` แทนที่ไฟล์เป้าหมายแบบอะตอม เนื่องจาก `File.Move` ในระบบไฟล์เดียวกันคือการเปลี่ยนชื่อ ระบบปฏิบัติการรับประกันความเป็นอะตอม — จะเห็นเฉพาะไฟล์เก่าหรือไฟล์ใหม่ ไม่มีสถานะระหว่างกลาง |
